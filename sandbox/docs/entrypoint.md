# Entrypoint

Container boot sequence: `entrypoint.sh`, its sourced `lib/` helpers, and the root phase that runs before privileges drop — plus every `docker exec` call site the launcher (`watch/internal/sandbox/launcher`) assembles, since the privilege-drop guardrail below governs both.

## Rules

- **Never self-remap the UID/GID of a running account via `usermod`/`groupmod`.** A live account's own UID/GID cannot be renumbered while any process (including the calling shell) runs under that UID — the utilities refuse the operation. Container entrypoints that need to remap their own running user (e.g., to match host UID for mounted volumes) must start privileged (root) with zero workload processes yet alive, perform the remap safely, then unconditionally drop privileges to the target user before the rest of the entrypoint runs. Do not try to self-remap from within the account being changed.

- **`docker run --user X` persists for the container's lifetime — it is not scoped to the initial process.** The `--user` flag is stored as the container's `Config.User` and becomes the default for every subsequent `docker exec` call that doesn't pass its own explicit `-u` flag. A pattern that starts a container as root for setup (privilege-drop), but then runs workload via `docker exec`, will silently run all exec calls as root if they omit `-u <target-user>`. The image's original `USER dev` directive from the Dockerfile does not automatically restore as the default for exec — you must audit and add explicit `-u dev` to every exec call site after a privilege-drop entrypoint.

- **TTY detection via permission-bit check alone is unreliable in sandboxed environments.** A permission check like `[ -r /dev/tty ] && [ -w /dev/tty ]` returns true even when `/dev/tty` exists with permissive bits but has no actual controlling terminal attached (common in Docker/CI containers) — an actual `open(2)` of the file will then fail with ENXIO. When a conditional behavior truly depends on interactive TTY availability (e.g., destructive-action confirmation gates), verify with an actual open attempt: `exec 3<>/dev/tty 2>/dev/null`, not just a permission-bit check.

- **Seeding a host credential file into the container must verify the file actually carries the credential, not just that it exists.** An `[[ -f "$staged" ]]` guard followed by an unconditional `cp` assumes the host stores the secret in that file — but credential CLIs increasingly default to OS-keyring storage and leave behind a config file that names the account with no token in it (e.g. `gh auth login` writes `~/.config/gh/hosts.yml` with no `oauth_token:` unless `--insecure-storage` is passed). The container cannot reach a host keyring, so copying that file in yields a config that is *worse than absent*: gh's multi-account migration aborts on an account whose token it can't resolve, breaking every `gh` call — including `gh --version` and including runs with `GH_TOKEN` set, since the migration runs on config load before auth resolution. Grep the staged file for the secret key before copying; when it's absent, skip the copy (so the CLI starts clean and env-var auth still works), never clobber a working in-container login with it, and warn to stderr naming the concrete remedy.

- **Seed a multi-file credential as one atomic set, never file by file.** The seed-once guard of #259 (`seed_credential`) reads naturally as a per-file rule, but some CLIs split one login across several files: `az` keeps the identity and its subscriptions in `~/.azure/azureProfile.json`, that identity's tokens in `msal_token_cache.json`, and service-principal secrets in `service_principal_entries.json`. Applying the guard per file lets a partially-populated destination — an in-container login whose token cache has not been written back yet — take the host's tokens alongside its own profile, splicing two identity chains into a login that fails in ways neither side explains. Gate the whole set on "does the destination hold *any* credential of this kind" (`seed_azure_creds` in `lib/seed-auth.sh`), and stage only the auth files: `~/.azure` also carries telemetry, command caches and logs that can reach hundreds of megabytes and have no business crossing the boundary.

- **Never recurse a `chown` (or any other metadata write) over a tree the launcher mounts into.** `/home/dev` and `/workspace` are not plain directories — the launcher bind-mounts host paths *inside* them, some read-only by design (`/home/dev/.gitconfig`, per `assembleVolumeMounts` in `watch/internal/sandbox/launcher/launch.go`). `chown -R` issues the `chown(2)` syscall unconditionally, without skipping entries that already carry the target ownership, so a single read-only nested mount returns `EROFS` and takes the whole recursive call — and, on the fatal remap path, the whole container — down with it (#1032). Re-own such trees through `lib/remap.sh`'s `chown_home_tree`, which prunes nested mount points read from `/proc/self/mountinfo`. Derive that prune list from `mountinfo`, never from a hardcoded path list: `.gitconfig` is only the mount that happens to land under `/home/dev` today, and the next one added would silently reintroduce the same startup failure.

- **A remediation hint in a failure message must be able to fix the failure it is attached to.** The remap's `chown` failure told users to run `cenci sandbox prune --volumes`, which cannot help when the offending path is a bind mount recreated from the host on every launch — it sent people to destroy their credential-bearing home volume for nothing and left the real cause unstated (#1032). When a message can't name a specific remedy, point at the concrete diagnostic (the failing path, the error above it) instead of guessing.

- **When adding new code to the root phase of `entrypoint.sh` or its sourced libs (like `lib/dind.sh`), systematically cross-check against ALL established conventions already present in the file.** Don't assume a pattern is obvious just because related examples exist nearby. Key root-phase conventions to verify: hardcoded `/home/dev/` paths (never `$HOME`, since root's `$HOME` is `/root`, not `/home/dev`), explicit exit-status checks on privileged calls like `groupadd`/`usermod` (fatal errors must fail loud), and `flush_boot_log; exit 1` before fatal exits (not bare `exit 1`, to avoid losing diagnostics to a SIGKILL race when not running under `--init`). Code reviewers often miss violations of secondary patterns if each reviewer assumes others verified those details; implementers should verify the full set before review.
