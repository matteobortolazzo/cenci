# Hook Events: Testing & Diagnostics

Patterns for implementing new `ipc.HookEvent` fields and event-handling logic to ensure correctness and diagnostics.

## Rules

- **Test JSON parsing via the real entry point, not struct construction.** When adding a new field to `ipc.HookEvent` that is parsed from external JSON (e.g., from Claude Code hooks), write an integration test that spawns the real `cenci notify` binary, feeds the JSON on stdin, and asserts that the field was parsed into the resulting `ipc.HookEvent`. Direct struct construction in daemon-level tests will pass even if the JSON tag is misspelled or missing — the real parse path will silently fail to populate the field, leaving the bug unfixed. The project has an established pattern for this: `TestNotifyCodexPromptSendsOnlyCompactTaskName` in `main_test.go` spawns the real binary and asserts on the received `ipc.HookEvent`. Ticket #277: `AgentID` field was added to `ipc.HookEvent` for subagent-scoped hook events, and daemon-level tests checked the guard logic by constructing `HookEvent{AgentID: "sub1", ...}` directly. A JSON-tag typo in `runNotify` would have silently remained while the daemon tests passed.

- **Log all event drops and suppression branches under `cfg.Verbose`.** The daemon's event-mapping pipeline (`internal/daemon/event.go`) is a status-accuracy component — bugs here silently cause wrong status reports. When adding a new drop or suppression path (e.g., a guard that returns `StatusUnknown` instead of a terminal status), add a `cfg.Verbose`-gated log line following the file's existing convention (e.g., line 27–29 for empty-session drops). If the guard ever misfires (e.g., a stray `agent_id` on a main-agent event), the log reveals it immediately; without logging, silent status misreports go undiagnosed. Ticket #277: the new suppression branch (subagent-tagged terminal events → `StatusUnknown`) was initially added without logging, reducing diagnosticability. Fix: add a `cfg.Verbose`-gated log line matching existing drop-path convention.
