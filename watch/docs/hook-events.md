# Hook Events: Testing & Diagnostics

Patterns for implementing new `ipc.HookEvent` fields and event-handling logic to ensure correctness and diagnostics.

## Rules

- **Test JSON parsing via the real entry point, not struct construction.** When adding a new field to `ipc.HookEvent` that is parsed from external JSON (e.g., from Claude Code hooks), write an integration test that spawns the real `cenci notify` binary, feeds the JSON on stdin, and asserts that the field was parsed into the resulting `ipc.HookEvent`. Direct struct construction in daemon-level tests will pass even if the JSON tag is misspelled or missing — the real parse path will silently fail to populate the field, leaving the bug unfixed. The project has an established pattern for this: `TestNotifyCodexPromptSendsOnlyCompactTaskName` in `notify_test.go` spawns the real binary and asserts on the received `ipc.HookEvent`. Ticket #277: `AgentID` field was added to `ipc.HookEvent` for subagent-scoped hook events, and daemon-level tests checked the guard logic by constructing `HookEvent{AgentID: "sub1", ...}` directly. A JSON-tag typo in `runNotify` would have silently remained while the daemon tests passed.

- **Log all event drops and suppression branches under `cfg.Verbose`.** The daemon's event-mapping pipeline (`internal/daemon/event.go`) is a status-accuracy component — bugs here silently cause wrong status reports. When adding a new drop or suppression path (e.g., a guard that returns `StatusUnknown` instead of a terminal status), add a `cfg.Verbose`-gated log line following the file's existing convention (e.g., line 27–29 for empty-session drops). If the guard ever misfires (e.g., a stray `agent_id` on a main-agent event), the log reveals it immediately; without logging, silent status misreports go undiagnosed. Ticket #277: the new suppression branch (subagent-tagged terminal events → `StatusUnknown`) was initially added without logging, reducing diagnosticability. Fix: add a `cfg.Verbose`-gated log line matching existing drop-path convention.

- **A field that crosses the container trust boundary is validated at daemon ingest, not only in `cenci notify`.** The event socket is mounted into containers, so any in-container process can write a raw event line that never went through `notify`. `tmux_socket` (#1429) is therefore checked in `Daemon.sanitizeTmuxSocket` (`internal/daemon/event.go`) before the session key is computed: `tmux.ValidSocket`, then the trusted directory from the `Daemon.tmuxSocketDir` seam (production `tmux.TrustedSocketDir`), then `tmux.CheckTrustedSocket`, in that order, and any failure, including an error resolving the directory, leaves the socket empty (the default server) and logs one `cfg.Verbose`-gated line naming the event type, the session key and the error class (`malformed` or `untrusted`); a malformed value is never echoed. `notify` does not pre-validate: it sends the first field of `$TMUX` as is and the daemon is the authority. Test it by writing a raw JSON line to a real `ipc.EventReceiver`, since the sanitizer cannot be exercised by constructing `ipc.HookEvent` through `notify`.

- **The `native-measurement` kind is lifecycle-neutral display data (#1450).** A line `{"kind":"native-measurement","measurement":{...}}` on the event socket routes to its own `EventReceiver.NativeMeasurements()` channel, never to `Events()`, and the daemon loop hands it to `applyNativeMeasurement` instead of `handleEvent`. Its top-level keys are exactly `kind` and `measurement`, so a pre-change daemon decodes it as a `HookEvent` with an empty `session_id` and `tmux_pane` and drops it. Rules:
  - It never creates a session and is stored only on an already-tracked session, looked up by `d.sessions[session_id]` alone (no `pane:` fallback). An untracked, ended or invalid session id is dropped.
  - It never changes status, `LastEvent` or `BackgroundHold` and never reaches `frontend.OnEvent`, so measurements cannot keep a session alive past the TTL. A sample whose `measured_at` is not strictly newer than the stored one is dropped (late, reordered or duplicate delivery).
  - The receiver checks only that `measurement` is a JSON object (carried as `json.RawMessage`, so one bad field cannot fail the whole decode). The daemon re-validates every field through `measurement.Parse`, because containers write to the same socket: a bad `session_id`, `measured_at` (missing, not RFC 3339, or more than 5 minutes ahead of the daemon clock) or non-object body drops the whole sample, while any other bad field is rejected alone and named in the snapshot's `native_measurement.missing` (absent or rejected) and `invalid` (rejected only) lists.
  - A `rate_limits` array with more than `measurement.MaxRateLimitEntries` (8) entries is rejected as the single field `rate_limits` (`quota` null, no per-entry paths). Every entry adds `missing`/`invalid` paths, so without the cap one 4 KiB socket line would store a ~100 KB measurement, push the broadcast snapshot past the client's 64 KiB line limit (`watch.ReadSnapshot` fails with `bufio.ErrTooLong`) and blind every reader.
  - Every daemon-side drop is logged under `cfg.Verbose`, and the log line never carries raw producer bytes. The receiver's own drops (invalid JSON, a non-object `measurement`, a full channel) are logged unconditionally, like the pending-close path. A bare `NaN` token is not valid JSON, so the receiver drops that whole line before the daemon sees it (a per-field rejection applies to the string and overflow forms such as `"NaN"` and `1e999`).
  - A sample accepted with a `measured_at` up to `FutureTolerance` (5 minutes) ahead of the daemon clock makes later samples with an older or equal `measured_at` drop until time catches up; the effect is bounded by that tolerance. The indexes in `missing`/`invalid` (`rate_limits[<i>]...`) refer to input array positions, not positions in the stored `quota` slice, because a rejected non-object entry is skipped in `quota`.
  - The snapshot field is the additive `WindowState.NativeMeasurement` (`native_measurement`, omitted when nil). Freshness (`stale` after 15 minutes) and quota state (`expired (reset passed)`) are not stored: `measurement.Freshness` and `measurement.QuotaState` derive them from the reader's clock. A context `percent` above 100 is stored with `over_window: true`, not clamped.
