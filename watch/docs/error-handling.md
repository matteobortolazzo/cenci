# Error Handling

Rules for error classification, sentinel errors, failure visibility, and default-deny behavior across the watch codebase.

## Rules

- When introducing a new sentinel error for detection via `errors.Is()`, add a direct unit test at the package boundary asserting the sentinel is returned and detectable — do not rely on indirect coverage via higher-level integration tests, as a refactor could silently break `errors.Is()` while indirect tests still pass (#412).
- When testing error handling where the same code path can return multiple distinct failure classes, use error-content-specific assertions (e.g., `strings.Contains(err, "specific-marker")`) for each case, not just empty/non-empty checks. A non-empty check alone would pass identically if a regression collapsed multiple classes into the same placeholder string, allowing the tests to silently stop distinguishing between them (#446).
- When extracting or reusing a helper function in a new caller with different error stakes (e.g., from informational use to decision-gating), re-examine the helper's error-handling contract even if the extraction preserved existing behavior and tests—a silent-on-error default acceptable in a low-stakes context may mask errors in higher-stakes decision paths (#560).
- When a diagnostic or collection function calls multiple independent read helpers (image metadata, plugin manifests, logs, container inspection), all helpers must use the same failure-visibility strategy — either all show unknown/unavailable placeholders and append `SeverityWarning` findings on read failure, or all silently omit sections. Mixing patterns makes the report ambiguous: readers cannot distinguish 'read failed' from 'no data to display.' See `Diagnose()` in `watch/internal/sandbox/launcher/diagnose.go` for the `versionOrUnknown` pattern (#572).
- When implementing error-type classification for a code path that can fail in multiple distinct ways (e.g., an `os/exec` command failing either because 'no such container' or 'daemon unreachable'), check the same package for existing classification patterns (e.g., `errors.As(err, &exitErr)`, type assertions on `*exec.ExitError`, or sentinel-error checks) before inventing new error handling. Reusing patterns reduces code divergence and prevents silent classification breakage during future refactors — see `readHomeVolumeFile` in `watch/internal/sandbox/launcher/launch.go` and `containerStartupState` in `diagnose.go` (#572).
- When adding a new parser, validator, or derivation function for a security/safety decision, check its default behavior on malformed/empty/truncated input—does it default permissive or default-deny on error? Before finalizing, grep the file/package for established conventions in similar functions (e.g., `containerHasSharedAgentMount`, `containerStartupState`); if they follow a "default deny" pattern, your new function should too. Deviating silently risks pattern inconsistency that code review may miss, especially when the deviation takes the "safer-looking" but actually-permissive default. In #628, `parseReusePosture` silently returned zero-value (permissive, interpreted as "no host socket") on malformed `docker inspect` output, the only function in `launch.go` to default permissive instead of deny; the inconsistency went undetected until review (#628).
- When a function returns `(value, ok bool)` and is called at multiple call sites within the same logical invariant or comparison (e.g., comparing rank of both current and target stages using `stageRank(current)` and `stageRank(target)`), apply the default-deny discipline uniformly to every call site—not just the one handling external input. It's easy to reason "that side looks reachable by hostile input, so it needs the ok check" and miss the same function's ok discarded on the other side of the comparison. An unregistered/missing value on the unchecked side silently degrades to zero, canceling the default-deny guard on the other, making the entire invariant permissive when only half was intended to be (#636).
- When a helper returns (partial results, error) from concurrent or sequential operations (e.g., `RuntimesWithVolume` querying both docker and podman, returning owners found plus an errors.Join of any query failures), callers must handle both together: appending the error to an error aggregation list and proceeding with the partial results, not treating non-nil error as fatal to using the partial results. One runtime's listing failure doesn't invalidate another runtime's successful query or the action the caller intends to take against it (#629). Write explicit regression tests for this case (e.g., `TestSandboxUpdateAgent_OneRuntimeVolumeQueryFails_HealthyRuntimeStillUpdatedNonZeroExit`) where one runtime's query fails but the other succeeds, to prevent silent regressions where error-return refactors collapse back to treating any error as fully fatal.
- When establishing a security or safety principle for handling one class of malformed/anomalous input (e.g., "missing/unknown data ⇒ treat as stale/unsafe"), systematically audit ALL related malformed-input or anomalous-data classes that should fall under the same principle before finalizing—do not stop at the case the ticket text called out. Examples: if missing timestamps → stale, also audit future/corrupted timestamps and ensure they follow the same principle; if unparseable env var → error, also audit valid-but-huge values (overflow-risking) and bound them before arithmetic. Write explicit test cases for each edge case. In #710, missing timestamps were correctly treated as stale, but future-dated timestamps (which should also be stale) and overflow-risking TTL hours (which should be bounded) were not initially audited, requiring security-review findings and rework (#710).
- When implementing a safety guard or invariant that depends on identifying a critical entity for security purposes (e.g., "never attach the main checkout"), derive that identity from the authoritative system answer (`git worktree list --porcelain`, filesystem stat, container runtime API, etc.), not from caller-supplied parameters or override flags used for testing — the test hook value is valid for initialization only, never for security-critical identity comparisons. A caller-supplied value can be spoofed to bypass the guard; the system's own answer cannot be. Example: `AttachWorktree` validates against `records[0].Path` from `git worktree list --porcelain` (the authoritative repo-wide answer), not against `resolveMainRoot(o.RepoRoot)`, which returns the caller-supplied `--repo` test hook verbatim — a caller could point `--repo` at a linked worktree to disguise the true main checkout and bypass the guard if the override were trusted instead (#688).
- Never write `if err != nil || benignCondition { return PermissiveOutcome }` in any re-verification or safety-gating decision — this pattern silently collapses command error with a legitimate benign condition, violating the error/benign separation principle. Handle them in distinct branches: `if err != nil { return ErrOutcome; }` followed by `if condition { return BenignOutcome; }`. This matters especially when re-verifying a state during a window where intervening operations have happened (e.g., re-checking `HEAD` branch after a network call, re-probing git state after a fetch that could have failed): a probe error must not silently fold into "state is different" (permissive). The pattern is easy to miss when hastily implementing a similar check near an earlier, correctly-written check in the same function. Grep the same function for established error-handling patterns before finalizing (#822).
