# tmux Behavior

Lessons on non-obvious tmux command behavior that differ from API expectations or vary by version.

## Rules

- **Unscoped tmux target resolution honors $TMUX_PANE environment variable.** Commands like `tmux display-message -p "#{session_name}"` (without `-t`) do not resolve to the server's most-recently-active session; tmux's cmd-find logic prioritizes any valid `$TMUX_PANE` from the client's environment ahead of most-recent-session, even ahead of a genuinely attached client on another session. This behavior is version-dependent (confirmed on tmux 3.4). When a test's red state depends on an external binary's resolution behavior, verify it empirically against the installed version before committing to the mechanics — do not assume unscoped forms ignore environment variables.

- **`tmux display-message -t <nonexistent-pane> -p "#{fmt}"` exits 0 with empty stdout instead of erroring.** Unlike most tmux subcommands (e.g., `rename-window`, `list-panes`), `display-message` with `-p` does not fail when the `-t` target is invalid; it succeeds silently with empty output. Production code must include an explicit empty-output check when a non-empty value is the contract — do not assume a tmux subcommand will error on an invalid target.

- **Status symbols belong in user variables, not window names.** Embedding a status symbol (▶, ✓, !, ~) directly in a window name breaks custom `status-format` configs: it doubles up with the config's own indicator inside `#W`, hardcoded colors override `window-status-style` changes, and users can't reference or control the symbol from their format strings. Set symbols via the `@cenci-symbol` user variable (per window) and style via `@cenci-style`; window names should contain only the task name or original name. For default-format users, prepend `#{@cenci-symbol}` to `window-status-format`/`window-status-current-format` during tracking and restore on cleanup.

- **`tmux has-session -t <name>` prefix-matches unless the target is exact-match-forced with a leading `=`.** `tmux has-session -t work` reports true against an unrelated session named `work-2` (and any other session whose name starts with `work`), because tmux's target-session resolution falls back to prefix matching when no exact name match exists. A probe that must confirm one specific named session exists — never a same-prefixed sibling — has to use the exact-match form `tmux has-session -t =<name>` (ticket #927, `internal/tmux.ExecClient.HasSession`). A nonzero exit (no such session, or no server running at all) is a normal "absent" result, not a command failure — callers should not treat it as noteworthy beyond the negative boolean.

- **Exact matching must continue after the session probe.** The grouped-session check and window creation carry the same leading equals marker used by the existence probe. The post-create window option exact-matches both the session and the independently parsed window name. Otherwise either target can disappear after the probe or creation and a bare target can resolve to a same-prefixed sibling. User-facing config, dry-run output, and errors keep the raw session name. Raw names that begin with an equals sign receive a separate exact-match marker. See ticket #937.

- **`tmux` transmits its client's full environment (and file descriptors) to the server during the `MSG_IDENTIFY_ENVIRON` handshake — use an allowlist when the socket target is attacker-controlled.** When `tmux -S <socket>` connects to a server, the client's entire environment is forwarded to that server; a hostile server can exfiltrate secrets (API keys, tokens, etc.). Do not scrub a denylist of known vars (e.g., TMUX, TMUX_PANE) from `os.Environ()` and forward the rest—this leaves secrets exposed. Instead, build the child env from scratch using an explicit allowlist (PATH, HOME, TERM, LANG only, populated only if set in the current process, via `os.LookupEnv`, never fabricated). The `CENCI_TMUX_SOCKET` is attacker-controlled—any container process can set it—so the reaper uses `buildMinimalTmuxEnv()` to construct the allowlist env for tmux queries (#1007). Socket-path shape validation gates syntax errors but doesn't prevent dialing hostile sockets; the allowlist env is the exfiltration defense. Future work (#646) will restrict socket paths further; the allowlist behavior applies independently and immediately.

- **Always pass an explicit `-S <path>` rather than relying on ambient `$TMUX`/`$TMUX_PANE` ownership resolution.** `cenci sandbox reap-orphans` is self-exec'd by the daemon (`internal/reap`), a process whose own `$TMUX`/`$TMUX_PANE` may be unset entirely or may point at a server unrelated to the containers' panes it's classifying — the first "unscoped tmux target resolution honors `$TMUX_PANE`" rule above means an unscoped query would silently resolve against the *reaper's* ambient pane instead of the socket a container actually reported, misclassifying liveness. The reaper resolves each `(socket, pane)` pair with an explicit `-S <socket>` per query, never bare `tmux` (#1007).
