# JavaScript / JXA Frontend Patterns

Conventions and gotchas specific to JavaScript-for-Automation (JXA) and JavaScript frontends in cenci plugins.

## Rules

- **`new Date(string)` does not throw on unparseable input — validate with `isNaN(date.getTime())`**. In JavaScript, `new Date("unparseable")` silently creates an `Invalid Date` object. Calling `.getHours()`, `.getMinutes()`, or other date methods on `Invalid Date` returns `NaN`, rendering misleading UI (e.g., "last run NaN:NaN" with no error indication). Always check `isNaN(date.getTime())` after parsing and fall back to rendering the raw input string on failure, keeping malformed data visible. This mirrors the Go pattern in `status.go` where `time.Parse` errors are caught and the raw RFC3339 string is rendered as fallback. See `plugin/macos/cenci.5s.sh` (the `isNaN(runDate.getTime())` guard in the dispatch-summary block) for the correct pattern.
- **Never inline a JXA heredoc inside a `$( ... )` command substitution — put it in a function body and substitute the call**. macOS `/bin/bash` is bash 3.2.57, and GUI launchers (SwiftBar and friends) run plugins with a minimal PATH, so a `#!/usr/bin/env bash` shebang resolves there rather than to a Homebrew bash 5. bash 3.2 applies shell quote rules while scanning a command-substitution body and does **not** exempt a quoted heredoc nested inside it, so a single apostrophe anywhere in the JXA source — a possessive in a JS comment is enough — opens a single-quoted string that swallows the rest of the file. The script then dies at parse time with ``unexpected EOF while looking for matching `"'`` reported on the last line, producing no output at all. Wrap the heredoc in a shell function and call it from a small `$( ... )` instead. Syntax-checking with a modern bash will not catch this: pin it with an explicit `/bin/bash -n` check plus an end-to-end `/bin/bash "$PLUGIN"` run in the plugin's test suite (see `plugin/macos/test.sh` Case 0).
