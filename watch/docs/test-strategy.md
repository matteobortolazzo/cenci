# Test Strategy Verification

Lessons on validating test assumptions, keeping fakes and fixtures honest, and ensuring direct coverage for behavior the plan did not enumerate.

## Rules

- **Verify test strategy assumptions against actual code behavior before Q&A approval.** When a plan's approved test strategy depends on the control-flow or behavior of existing code outside the plan's declared file scope, examine that existing behavior and verify it actually supports the proposed observable. Don't assume or infer behavior from context; read the function. In ticket #122, the plan's Q&A approved a "log-buffer proxy" test strategy that required `CollectTickets` to attempt all configured repos even after one fails (to log newly-enrolled repos). The function actually had fail-fast behavior (return immediately on first repo error), making the test strategy unimplementable against unmodified code—a gap the planning phase didn't catch because `collect.go` wasn't in the declared plan scope. Planning scope and test strategy scope are distinct; if the test depends on a function's behavior, include that function in the verification process.

- **Write direct, dedicated tests immediately for unplanned code changes that support the plan's test strategy.** When implementation discovers that a file outside the plan's declared scope must be modified to make the approved test strategy work, write a direct unit test for that specific behavior change right away—don't rely on incidental coverage from integration tests or the original test suite. In ticket #122, the implementer changed `CollectTickets` from fail-fast to best-effort (attempt all repos, join errors) to unblock the approved reload tests. That change was only incidentally covered by the reload tests' log-substring assertions, not by a direct test of "CollectTickets attempts all repos and joins errors". The gap was caught during code review, requiring a follow-up delegation to add `collect_test.go`. Direct tests surface the behavior change explicitly and prevent reviewers from having to infer it.
- **Grep for ALL mock implementations when changing test infrastructure.** When a test infrastructure change (new environment variable, mock parameter) requires updating multiple mock implementations or test helpers, grep for ALL of them before committing—in particular, fake `docker inspect` / `image inspect` fixtures appear across multiple test files (`engine_test.go`: buildEngine, volumeCheckEngine; `sandbox_open_test.go`: writeScriptedRuntime, openTestEnv, batchEnv) and must stay in sync. Missing even one location can silently cause end-to-end tests to exercise different code paths than unit tests, even when both pass (#493).
- **Audit existing tests when adding a new external-command call, and clear the test cache.** When adding new external-command calls (e.g., `docker ps`, `docker inspect`) to a code path, audit all tests exercising that path — pre-existing tests that construct minimal fakes (e.g., `Engine{Runtime: "docker"}` without putting a fake binary on PATH) will fail when the new code attempts to invoke the command. Use `go clean -testcache` to avoid test-cache masking failures in previously-cached test packages — a `go test ./...` pass with stale cache does not validate newly-added external calls (#620).
- **Add a regression test and comment when changing side-effect ordering.** When refactoring code that performs side effects and changing the order of operations (e.g., moving container cleanup before vs. after validation), explicitly add a regression test and comment documenting the new ordering — do not assume existing tests will detect the behavior change. Code-review confirmation is not a substitute for a test assertion of the specific ordering (#620).
- **Never wrap multi-line shell-fake output in `$(...)`.** In shell test-fake helpers that output entire multi-line values for use as verbatim fake output (e.g., FAKE_LOGS, FAKE_BOOT_LOG), call the helper function directly as a statement rather than wrapping it in `$(...)` command substitution — command substitution unconditionally strips every trailing newline, silently corrupting multi-line values. Reserve `$(...)` for scalar single-line values and helper compositions. See `sandbox_open_test.go`'s `fv`/`fvb` pattern (#629).
- **Verify why a fixture makes an assertion pass before building on it.** When a test's fake/mock setup makes an assertion pass because of how the fixtures are shared (e.g., unscoped `FAKE_VOLUMES` shared by both docker and podman fakes, causing both runtimes to genuinely report ownership), verify the fixture's *cause* — why does the setup produce this result? — before implementing code that only uses part of the fixture's output. Test-passing alone doesn't validate that the code matches the design intent, especially when that design explicitly names "every owner" and the fixture's shared state accidentally makes "both owners" work with "owners[0]" — the bug hides until you audit why the fixture made the test pass. When the test's expected behavior contradicts an explicit design or AC statement, that discrepancy is a red flag to investigate the fixture before shipping (#709).
- **Capture frontend state before the mutating operation, and test every closure path.** When implementing a cleanup or prune function that depends on frontend state (e.g., `WindowInfo()`) which a concurrent sweep or teardown operation will invalidate, capture that state before calling the mutating operation, not after — `Sweep()` and `forgetWindow()` tear down the frontend's session/pane tracking, making references unavailable for post-operation cleanup. Add explicit tests for all session-closure paths (SessionEnd-driven, pane-gone sweep), not just the primary case, to verify the cleanup actually executes and mitigates its intended risk (#522).
