# Test Strategy Verification

Lessons on validating test assumptions, keeping fakes and fixtures honest, and ensuring direct coverage for behavior the plan did not enumerate.

## Rules

- **Verify test strategy assumptions against actual code behavior before Q&A approval.** When a plan's approved test strategy depends on the control-flow or behavior of existing code outside the plan's declared file scope, examine that existing behavior and verify it actually supports the proposed observable. Don't assume or infer behavior from context; read the function. In ticket #122, the plan's Q&A approved a "log-buffer proxy" test strategy that required `CollectTickets` to attempt all configured repos even after one fails (to log newly-enrolled repos). The function actually had fail-fast behavior (return immediately on first repo error), making the test strategy unimplementable against unmodified code—a gap the planning phase didn't catch because `collect.go` wasn't in the declared plan scope. Planning scope and test strategy scope are distinct; if the test depends on a function's behavior, include that function in the verification process.

- **Write direct, dedicated tests immediately for unplanned code changes that support the plan's test strategy.** When implementation discovers that a file outside the plan's declared scope must be modified to make the approved test strategy work, write a direct unit test for that specific behavior change right away—don't rely on incidental coverage from integration tests or the original test suite. In ticket #122, the implementer changed `CollectTickets` from fail-fast to best-effort (attempt all repos, join errors) to unblock the approved reload tests. That change was only incidentally covered by the reload tests' log-substring assertions, not by a direct test of "CollectTickets attempts all repos and joins errors". The gap was caught during code review, requiring a follow-up delegation to add `collect_test.go`. Direct tests surface the behavior change explicitly and prevent reviewers from having to infer it.
- **Grep for ALL mock implementations when changing test infrastructure.** When a test infrastructure change (new environment variable, mock parameter) requires updating multiple mock implementations or test helpers, grep for ALL of them before committing—in particular, fake `docker inspect` / `image inspect` fixtures appear across multiple test files (`engine_test.go`: buildEngine, volumeCheckEngine; `sandbox_open_test.go`: writeScriptedRuntime, openTestEnv, batchEnv) and must stay in sync. Missing even one location can silently cause end-to-end tests to exercise different code paths than unit tests, even when both pass (#493).
- **Audit existing tests when adding a new external-command call, and clear the test cache.** When adding new external-command calls (e.g., `docker ps`, `docker inspect`) to a code path, audit all tests exercising that path — pre-existing tests that construct minimal fakes (e.g., `Engine{Runtime: "docker"}` without putting a fake binary on PATH) will fail when the new code attempts to invoke the command. Use `go clean -testcache` to avoid test-cache masking failures in previously-cached test packages — a `go test ./...` pass with stale cache does not validate newly-added external calls (#620).
- **Add a regression test and comment when changing side-effect ordering.** When refactoring code that performs side effects and changing the order of operations (e.g., moving container cleanup before vs. after validation), explicitly add a regression test and comment documenting the new ordering — do not assume existing tests will detect the behavior change. Code-review confirmation is not a substitute for a test assertion of the specific ordering (#620).
- **Never wrap multi-line shell-fake output in `$(...)`.** In shell test-fake helpers that output entire multi-line values for use as verbatim fake output (e.g., FAKE_LOGS, FAKE_BOOT_LOG), call the helper function directly as a statement rather than wrapping it in `$(...)` command substitution — command substitution unconditionally strips every trailing newline, silently corrupting multi-line values. Reserve `$(...)` for scalar single-line values and helper compositions. See `sandbox_open_test.go`'s `fv`/`fvb` pattern (#629).
- **Verify why a fixture makes an assertion pass before building on it.** When a test's fake/mock setup makes an assertion pass because of how the fixtures are shared (e.g., unscoped `FAKE_VOLUMES` shared by both docker and podman fakes, causing both runtimes to genuinely report ownership), verify the fixture's *cause* — why does the setup produce this result? — before implementing code that only uses part of the fixture's output. Test-passing alone doesn't validate that the code matches the design intent, especially when that design explicitly names "every owner" and the fixture's shared state accidentally makes "both owners" work with "owners[0]" — the bug hides until you audit why the fixture made the test pass. When the test's expected behavior contradicts an explicit design or AC statement, that discrepancy is a red flag to investigate the fixture before shipping (#709).
- **Capture frontend state before the mutating operation, and test every closure path.** When implementing a cleanup or prune function that depends on frontend state (e.g., `WindowInfo()`) which a concurrent sweep or teardown operation will invalidate, capture that state before calling the mutating operation, not after — `Sweep()` and `forgetWindow()` tear down the frontend's session/pane tracking, making references unavailable for post-operation cleanup. Add explicit tests for all session-closure paths (SessionEnd-driven, pane-gone sweep), not just the primary case, to verify the cleanup actually executes and mitigates its intended risk (#522).
- **When setting transient state fields directly in test fixtures, pin all dependent head/version/identity fields simultaneously.** When a test fixture sets `State` fields that depend on pre-existing value equality checks (e.g., `RepairPending` or `PendingKeys`), also set the matching head-SHA or identity fields (`LastHeadSHA`, `PendingHeadSHA`) that the pre-check logic compares against — otherwise, head-advance-detection logic (e.g., in `tick()`) will treat the state as stale relative to a new push and silently reset those fields *before* the code path under test executes, causing the test to exercise the wrong branch. The test passes with no assertion failure, silently masking incorrect code paths. Audit similar fixtures that directly mutate `State` fields to verify all dependent identity fields are pinned (#824).
- **In board/state-label fixtures, use realistic combined-label combinations, not isolated labels.** When writing regression tests for board/state-machine logic (e.g., `Reconcile`'s label-driven branches), construct test fixtures with the full set of labels that real entities carry in production, not just the single label being tested in isolation. In ticket #828, the `Working` label fixture omitted `Planned`, even though a `Working` ticket in production *always* also carries `Planned` (labels are added, never removed independently). The isolated fixture masked a branch-ordering bug: the `Planned` guard's `continue` fired for every `Planned+Working` ticket with a matched plan, starving the failure-recovery path permanently — the bug never surfaced in the simplified test. The fix narrowed the guard to `Planned && !Working` and updated the fixture to `["Working", "Planned"]`, revealing the latent bug and adding regression tests for the realistic combined-label scenario. Use fixtures that reflect production state to catch branch-order and state-machine logic bugs (#828).
- **A cross-module shared golden fixture needs a `runtime.Caller(0)` climb, a fail-closed-never-skip read, and its own CI path-filter registration.** When a fixture must be asserted independently by two different-language layers of the same repo (e.g. `flow/tests/adversarial-chain/fixtures/post-refinement-graph.json`, asserted by both the flow-side shell suite and `watch/internal/dispatch/chaingolden_test.go`), the fixture lives under the producing layer's own tree, and the consuming Go test resolves it via `runtime.Caller(0)` climbing out of the `watch/` module root (`internal/errcode/atlas_sync_test.go`'s precedent) — `go:embed` cannot cross the module root upward, so this is not a style choice. The read must `t.Fatalf` (never `t.Skip`) on a missing/unreadable/malformed file, since a moved or renamed fixture must break CI, not silently pass with zero coverage. Because the fixture's own path lives outside `watch/**`, a flow-only PR that edits it never triggers `watch-test` unless that path is separately registered in `.github/workflows/watch-ci.yml`'s `watch` path filter (`sandbox/tests/lib/**` is the existing precedent for the same cross-project reason) — omitting that registration lets the cross-layer contract drift one-sided (#912).
- **Test helpers that restore process state must always defer the restore call, never invoke it explicitly.** When writing a test helper that modifies process state (e.g., `os.Chdir`, environment variables, file system changes) and returns a restore function, always call the restore function via `defer` at the immediate call site, never later in the function. An early `t.Fatalf` or `t.Skip` between the state-changing operation and an explicit restore call will leave the process in a corrupted state (e.g., current working directory inside a since-deleted temp directory), breaking all subsequent tests in the same binary run. The pattern is: `restore := helperFunc(t); defer restore()` — make deferring the cleanup automatic at every call site, not optional (#855).
- **Understand subprocess-wrapper error propagation before writing tests that depend on it.** When implementing a test that depends on how a subprocess wrapper (e.g., `babysit.Run`, `exec.Command` shims, gh-CLI wrappers) handles errors from sub-operations, read the actual implementation of that wrapper first rather than inferring behavior from context. In ticket #914, `TestChainFake_Truncation` assumed `babysit.Run` returns `nil` on a `pr checks` read failure inside `tick()` — it actually propagates the error as `Run`'s own error in `--once` mode, requiring the test to expect that error and still assert `AutomergeFailureClass`. Wrapper behavior can be counter-intuitive; verify the actual control flow before writing assertions (#914).
- **Verify that a subprocess test double is actually in use, not the ambient real command.** When implementing a subprocess mock/fake (e.g., a fake `gh` binary placed in PATH), include a verification step that confirms the child process is actually executing your fake, not resolving to a real ambient command. A simple `exec.LookPath("gh") != nil` check passes equally for both fake and real binaries and doesn't actually verify identity. Compare the resolved path against the known test fixture directory (e.g., `filepath.Dir(resolvedPath) == shim.Dir()` or similar exact-path comparison) to ensure the child process is constrained to your test's fake implementation (#914).
- **Assertions proving a container is "not empty" or "not zero" are not sufficient for state-persistence tests.** When writing assertions for a test whose stated purpose is proving a specific piece of state persisted correctly or a counter incremented correctly (e.g., "verify this map entry survived `Save/Load`", "verify this counter incremented on retry"), assert the exact expected key/value or counter value, not merely that the container is non-empty or the counter is non-zero. A map-has-keys assertion or a "counter > 0" check passes under some regression cases and silently masks real bugs — for instance, the counter incremented under unintended code paths, or the map holds stale keys from prior test cases. Be specific: assert the exact entry `m["expectedKey"] == expectedValue` and exact count `c == expectedCount` (#914).
- **When a plan explicitly flags an assumption as "please verify" and provides literal text, preserve that text exactly in test assertions.** When a plan or ticket flags an assumption for verification (e.g., "please verify the arrow is literal") and consistently uses specific literal text (e.g., a Unicode character `→` vs. ASCII `->`, an exact command name, a specific format) across multiple sections, write test assertions using that literal text without substitution. Do not silently replace it with an ASCII-safe or equivalent alternative. If there's genuine doubt about whether the literal is intended, flag the ambiguity to the orchestrator or ticket author. Deviations silently introduced in test-writing propagate into implementation (since tests serve as ground truth) and require cross-file rework to correct (#933).
- **A failure/ambiguity-injection spec consumed by a re-exec'd fixture helper must be JSON-serializable through the persisted world, never a Go closure or parent-process table.** When a fake external boundary (e.g. `gh`) is served by a re-exec'd test-binary helper process, that process shares no Go memory with the parent test — a `var chainGhHook func(...)` or an in-process lookup table is invisible to it, and only something that round-trips through the persisted world JSON (a declarative kind + ordinal-call counter, per `chainfake_test.go`'s `ghWorld.Ambiguities`/`RouteCalls`) actually reaches the helper. Capture the real test-binary path (`os.Args[0]`) before any shim installer overwrites it, so a later re-exec spawns the test binary itself, not a recording/mutation shim. Inject a genuine timeout classification via the package's own deadline seam (e.g. `maxOpenPRProbeDuration`, overridden to a short bound) plus a blocking (never sleeping) shim — a real syscall block on an unclosed pipe read terminates immediately under a deadline kill, giving the real error classification in milliseconds with no `time.Sleep` and no multi-second `WaitDelay` hold (#914).
