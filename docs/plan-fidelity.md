# Plan fidelity — implementation vs. stated intent

Conventions for cross-checking an implementation against every section of its plan or
ticket — not just the literal "Files to Modify" wording — before treating the plan as
fully satisfied.

## Rules

- When implementing a pattern or check that already exists elsewhere in the same file or codebase (e.g., a grep check, a validation guard, error-handling convention), audit existing examples first to match established conventions — do not implement solely from a plan description. This includes error-handling specifics like stderr redirection; implementing a similar check without those details is a silent failure that a reviewer is more likely to catch than an implementer.
- When implementing a feature from a plan with Assumptions or Risks sections, cross-check that your literal implementation aligns with those sections' stated intent, not just the Files to Modify wording. If different sections contradict (e.g., intent says "empty label is not a drift case" but Files to Modify lists a condition that treats any mismatch as drift), flag the contradiction for clarification before committing — do not resolve it by choosing the most literal section (#493).
- When implementing a child ticket within a parent epic that specifies 'Key design decisions' or similar intent-setting context, verify that documentation examples and placeholder values align with that parent epic's stated purpose — do not rely solely on generic plausibility (e.g., HTTP endpoints, standard test frameworks) that might contradict the parent context (e.g., offline-only checks) (#505).
- In fallback logic where ground truth is unrecoverable (lost context, inaccessible data, compacted state), distinguish sharply between 'what default label/value is safe to report' vs. 'can we assert that a specific claim actually occurred'. Never default to asserting a false-assuring claim (e.g., "security review done") when you cannot verify it — instead report the gap honestly (e.g., "status unknown, verify manually") (#525).
- When implementing an acceptance criterion that says "verify X against the real system," a reviewer-accepted rationale for "why implementation approach A is wrong" does not authorize skipping the criterion entirely. If approach A is deemed unsuitable (e.g., enforcing table row order against real docs that use a different correct order), a narrower, correctly-scoped alternative often still exists and is still required (e.g., pairwise orderings that are already true today in the real system). An accepted "no to approach A" is not a "yes to zero implementation" — dig for the real-system-specific check that approach A was trying to approximate (#524).
- When an acceptance criterion specifies that two outcomes must be distinct (e.g., "distinguish a failed gate from a script error with distinct diagnostics"), verify that each outcome is explicitly created, tested, and reported separately — passing test suites alone do not verify that outcomes are actually distinct if the implementation could silently collapse them into one identical stop message. Each distinct outcome requires an explicit test case that exercises it independently (#555).
- When a plan's Risks section explicitly documents an architectural constraint or boundary condition (e.g., "state file at path X is not visible in worktree Y because git rev-parse --show-toplevel resolves differently per-tree"), do not apply the same logic uniformly across all code paths that would encounter that constraint. Example: a multi-stage CLI pipeline where early stages run in main checkout and late stages run in a feature worktree — if the plan flags that shared state becomes unavailable at the boundary, late-stage error handling must treat state-file lookup failures as expected (informational warnings, fallback to existing procedures), not authoritative hard-stops. Respect the architectural constraint in implementation even when it requires divergent behavior (#558).
- When an Acceptance Criterion specifies that a feature must work with certain flag combinations or in certain modes (e.g., "feature X works with flags A and B"), the plan's Test Strategy table must enumerate explicit passing-case tests for those combinations—not just error-path scenarios or partial cases. Cross-check the Test Strategy table against each Acceptance Criterion's scope before implementation starts; a plan with incomplete test coverage won't catch missing test cases until code review (#589).
- When implementing a method by mirroring an existing one (especially when an acceptance criterion specifies comprehensive coverage like "for each detected element"), verify field-by-field that your implementation addresses every field, slice, or collection the reference method iterates—the mirroring instruction is conceptual guidance, not a guarantee of structural coverage parity. Audit the reference implementation's loop structure before committing; a method can mirror another's purpose while silently omitting an entire category the reference already handles (#594).
- When editing documentation based on verification that a claim about system behavior is false (e.g., 'automated checks run during `/cenci:implement`'), verify your finding against the actual implementation source files where the behavior is defined—not adjacent modules or related documentation files. Absence of reference in a plausible-but-wrong file does not prove the claim false. Additionally, cross-check your edit against the ticket's Scope and Acceptance Criteria — if they explicitly require the claim to be documented, removing it violates plan fidelity (#533).
- When a plan's Risks section explicitly names a mitigation strategy involving defensive coverage (e.g., "redaction of secrets from user-facing output" or "truncation to prevent stack-trace leakage"), implement broad coverage for all realistic variants of that risk category—not just the single most-obvious pattern. For example, a secret-redaction function should cover `NAME=value`, `Bearer token`, `key:value`, JSON-quoted `"key":"value"`, and URL userinfo patterns, not only variable assignments. A test exercising one pattern does not verify the broader defensive goal. Treat the risk category and mitigation intent as the scope; the minimum implementable pattern is insufficient (#534).
- When a test's mock assertion differs from a security-sensitive specification in the plan's Q&A, Acceptance Criteria, or other decision-bearing sections, adjust the test's mock to match the plan—never adjust the security parameter to satisfy the test. Test scaffolding is subordinate to plan specifications. This pattern is especially critical for cryptographic or authorization checks where a test's convenience (e.g., matching an unescaped regex substring) can silently weaken security if it outranks the plan's locked decision (#626).
- All tests enumerated in a plan's Test Strategy table must be written and exercised during the phases assigned to them (e.g., Phase 3 for red tests, Phase 4 for implementation-verified tests). A Test Strategy row is a binding checklist item, not optional scaffolding. Omitting a row leaves the ticket incomplete and risks reviewer catch-up during code review. Cross-check the Test Strategy table against work completed before declaring each phase done (#626).
- When implementing security-critical deny rules using prefix matching (e.g., Bash permission filters, git command restrictions in `permissions.deny`), cross-check each rule against every invocation style documented or visible in the codebase. Prefix-matching rules only block commands that start with the exact prefix; commands invoked with global flags before the subcommand (e.g., `git -C <path>`, `git -c <config>`, `git --git-dir=`) will silently bypass rules written for bare subcommand form. If the plan's Architectural Context or other sections document that a certain flag style is used throughout the codebase, verify that deny rules account for all those patterns—or they will fail to protect against the project's own invocation conventions. Grep the codebase for the target command's actual usage patterns before finalizing rule coverage (#739).
- When a plan's Assumptions section or Files to Modify sections reference behavior, field names, or output shapes from an existing CLI/API (e.g., 'read the branch field from artifact --get output'), verify the actual contract against the implementation before finalizing the plan—do not assume the named field or output structure exists. A plan depending on a nonexistent field or invocation style requires implementation rework, and dependent documentation edits written based on that assumption become misleading. Verify the actual output shape, field names, and method signatures by reading source code or invoking the real CLI in a test repo before formalizing them in a plan or dependent doc-edit instructions (#688).
- Refactor phases must not override decisions the approved plan explicitly reasoned about — if renaming, reorganizing, or restructuring something the plan called out directly, that plan reasoning is binding unless refactoring reveals a fundamental error.
- When a ticket directs you to point to a recovery tool (e.g., `cenci diagnose`, error codes, or a diagnostic command) within failure documentation or a failure-handling branch (skill step, error atlas entry, status report, etc.), verify the tool's actual applicability and preconditions against that specific failure context — do not mechanically add the pointer just because the ticket's wording said to. Example: `cenci diagnose <session>` requires an already-launched/running session and provides diagnostics for launch-time failures and session health, not for image build failures; pointing to it in an image-build-failure recovery branch is factually wrong and would cause users to run a command with no meaningful output. Instead, verify when the tool applies (e.g., "if image builds successfully but `cenci open` launch fails") and rescope your documentation pointer to that correct failure point (#777).
- When a plan's Assumptions, Risks, or rationale sections make specific factual claims about existing code behavior (e.g., 'the glob ignores subdirectories', 'the script outputs field X', 'automated checks do not run during phase Y'), verify those claims by reading the source code before accepting the plan's scope. If verification shows the claim is false, the plan is incomplete — flag the discrepancy for clarification rather than implementing the stated scope which cannot satisfy the stated acceptance criteria. A factually false premise in a plan's reasoning invalidates the plan's scope, even if the plan's wording seems unambiguous (#776).
- When implementing file operations (archiving, moving, cleanup) that target gitignored directories (like `.plans/`) which exist only in `<repo-root>` and are never copied into the worktree, use `<repo-root>` for path resolution, not `<worktree-path>`. Gitignored state is created during Phase 1 (planning) in the main checkout before the worktree is spun up in Phase 2, so it is never present in the worktree. Using `<worktree-path>` results in a silent no-op that passes all tests because the operation itself (archiving, moving) has no automated assertion — the failure is purely behavioral/procedural. This is an exception to the general Phase 4 convention to anchor paths to `<worktree-path>` (#776).
- When a ticket directs you to "mirror an existing canonical implementation's technique" (especially for security-critical checks like collision-safe dedup matching), apply the technique *consistently across all branches and decision-tree paths* — not just the branch explicitly called out as needing a fix. A partial mirror that copies a defensive technique to one path (e.g., the fallback ticket-number match with complete-line `grep -qF`) but leaves another path's pre-existing defect unexamined (e.g., the primary URL match as a substring check) silently leaves the same vulnerability class unresolved on one path. Before finalizing your mirror implementation, audit *every* branch of the reference implementation where the mirrored technique should apply, not just the one mentioned in the ticket description. A selector that "looks like" a faithful mirror at a glance may apply the new technique to only the explicitly-called-out branch while missing other branches with the same property (#772).
- When a plan justifies an accepted cost or architectural compromise by citing an analogy to existing behavior (e.g., "cost matches pre-existing `gh issue list` calls"), verify at implementation time that the scale, magnitude, and order-of-magnitude of the new feature's actual cost structure matches the precedent. Performance or cost analogies that appear equivalent in planning can break when actual implementation discovers a different cost model (e.g., single flat call vs. unbounded per-item fan-out, cost scaling from 1x to 50x per pass). If the analogy does not hold at actual implementation scale, escalate the finding during code review for plan adjustment rather than finalizing implementation against an invalidated assumption (#825).
- When a plan lists documentation updates in "Files to Modify" or "Implementation Order" sections (e.g., updating `README.md`, `docs/orchestration.md`, or skill manifests), those are binding deliverables — not optional nice-to-haves or follow-up items. Treat documentation updates with the same rigor as code changes: verify completion before sign-off, and flag any omitted doc updates immediately during code review rather than allowing them to slip into later PRs. A plan that names specific doc files is asserting those updates are necessary for the feature to be properly communicated; skipping them violates plan fidelity and leaves users or maintainers working from stale documentation (#851).
