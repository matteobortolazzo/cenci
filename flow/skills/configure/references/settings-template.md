# Settings Template

Read this file on every run, from step 4 in `phases/guidance-settings.md` (see `SKILL.md` `### Step Map`). It holds the rationale for the base `permissions.deny` list and the marker-bounded list itself that step 4 writes and heals into `.claude/settings.json`.

   The deny list is written with explicit word boundaries rather than the `:*` shorthand wherever the boundary is load-bearing: `Bash(git push --force *)` blocks a bare force-push while leaving `git push --force-with-lease` usable, which implement's PR phase depends on. Deny always overrides allow, so a permitted form must never be caught by a deny rule. `git -C <path>` (used by every phase), `git rebase`, `git branch -D`, `git worktree remove`, and unscoped `git config --get`/`--list` are deliberately **not** denied; the positive controls stay allowed under the shipped template (probe P1, probe P2, probe P3, probe P4, probe P5). Every statement about Claude Code's matcher in this file was observed in a `claude -p` probe run on Claude Code 2.1.322, except where a statement is marked inferred, and is recorded in `flow/docs/claude-bash-matcher-evidence.md`. Every result was observed under `--permission-mode manual --permission-prompts none` and not under `bypassPermissions`, the mode `cn` unattended sessions run in, so none of it is a claim about bypass-mode behavior; re-run that procedure before trusting it on another build or in another permission mode. One limit is inherent to prefix rules and is not covered: implicit-local `git config <key> <value>` writes are caught only for the enumerated code-execution keys: `git config x.y z`, a key outside that set, is not denied (probe H11; see also the case-variant gap below). Env-var prefixes need care, and the evidence is narrower than "not a gap": a deny rule is still matched through an env-var prefix and the git argv stays visible to it (probe S5, probe H1, tested version 2.1.322), and an env-prefixed command matched no allow rule and was auto-denied in the tested no-approval-surface mode (probe S5c, probe N-EV1); what happens to such a command under a bypass mode was not observed. But variables that carry the payload themselves (`GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0`, `GIT_DIR`, `GIT_SSH_COMMAND`, `GIT_EXEC_PATH`) are named by no deny rule, and wrapper forms (`env`, `sudo`) were not probed; in the tested mode the auto-deny is the only thing observed stopping them, and under a bypass mode nothing observed stops them.
   Claude Code does not strip `-C <path>` or `--git-dir=<path>` before matching a deny rule, so every deny group carries its own `-C`-prefixed mirror (probe S4a, probe S4b). A mirror is not full coverage: only `-C`, `--git-dir` and `--work-tree` are mirrored, and another global flag before the subcommand defeats the bare rule, observed for `--no-pager` and inferred for the rest (gap (a) below). The mirrors cover the force-push family, `push --mirror`, `push --delete`, `push --no-verify`, the refspec-force form `push * +*`, `commit --no-verify`, `reset --hard`, `clean`, `checkout --`, `restore`, `filter-branch`/`filter-repo`, `reflog`, `gc --prune`, `update-ref`, `replace`, `branch -f`/`--force`, `--config-env`, `--exec-path`, every `git config` scope-selector write form, the exec-key rules and `remote set-url`/`config remote.*`; each mirror has a probe row showing it denied. `--git-dir=`/`--work-tree=` have their own bare and `-C`-prefixed rules because no earlier rule matched either flag (probe S4b). Claude Code itself already closes three further gaps: `*` spans spaces and several flags, so the mid-position rules are effective (probe S3); a deny rule is applied to every `&&` segment of a compound command (probe S7); and quoting and backslash escapes are removed before matching, so a quoted key or flag is denied like its unquoted form (probe H2, probe H3, probe H4, probe H6, probe H9). Matching is case-sensitive (probe S1, probe S2), so the blanket `Bash(git -c *)` and `Bash(git -C * -c *)` rules cover every section-name case variant of `-c` (probe N-CU1, probe N-CU2) without catching the allowed `git -C <path>`.
   The config-key case-insensitivity fix covers only the four keys with non-lowercase spellings already in the rule set (`core.hooksPath`, `core.sshCommand`, `core.gitProxy`, `core.askPass`) in the `git config` forms. Remaining gap: an implicit-local `git config <UPPERCASE.key> <value>` write (e.g. `git config CORE.hooksPath /x`, also with a `-C <path>` prefix) is not denied, and a prefix rule cannot close it without also denying the allowed `git config --get`/`--list` reads (probe N-CG1, probe N-CG2). The `-c` forms of the uppercase keys are denied by the blanket rules (probe N-CU1, probe N-CU2), so only the unscoped write stays open.
   Other known gaps: (a) matching is a literal prefix match with no global-option normalization, so a global flag other than the three mirrored ones (`-C`, `--git-dir`, `--work-tree`) placed before a subcommand defeats that subcommand's bare deny rule, not only the `-c` rules. This is observed for one flag, `--no-pager`, and four groups: `-c` (probe S6, probe N-NP1), a force-push (`git --no-pager push --force origin HEAD`, probe N-NP2), `reset --hard` (probe N-NP3) and a global-scope `git config` write (probe N-NP4). That it holds for any other global flag and for every other deny group is inferred from those probes (one flag, four groups), not observed. This is an accepted gap: closing it needs an open-ended list of global-flag deny rules, so none was added; (b) the blanket `Bash(git -C * -c *)` also denies any later ` -c ` token, e.g. `git -C <path> grep -c foo` (probe N-BL3), an accepted cost because no skill or agent uses that form; (c) a command substitution inside a key (e.g. `git config core.hooks$(echo Path) /x`) was auto-denied and no deny-rule text was produced in the tested permission mode, so deny-rule coverage of command substitution is unjudged (probe H10); (d) the `-C` mirrors use `*` across spaces and quotes are stripped before matching, so they match their keyword anywhere after `-C`, including inside a commit message, and deny ordinary commands (a false-deny, fail-closed, accepted like the blanket-`-c` over-match in (b)): `git -C <path> commit -m "fix: restore pane focus"` is denied by the `restore` mirror (probe N-FD1), `git -C <path> commit -m "chore: clean up notes"` by the `clean` mirror (probe N-FD2) and `git -C <path> rev-parse --git-dir` by the `--git-dir` mirror (probe N-FD3). Skills do commit with `git -C <path> commit -m "<message>"`, so a message that contains a deny keyword is denied (probed: `restore` and `clean`, as above) while the same commit with a message that avoids them runs (probe N-FD5). Other keywords matched by the `*`-spanning mirrors (for example `replace`, ` -c ` and `push --force`) are inferred to behave the same way; they were not probed; passing the message with `git -C <path> commit -F <file>` keeps its text out of the matched argv and runs (probe N-FD4). No skill was changed and no mirror was narrowed. This is not an exhaustive bypass list, only the known ones.

   `gh api` destructive-method coverage denies `DELETE`/`PUT` (method-first and path-first, `-X`/`-XM`/`-X=`/`--method`/`--method=` forms — ten syntactic forms in total — plus lowercase mirrors) so the probed `DELETE`/`PUT` spellings of the path-only `Bash(gh api repos/:*)` grant are denied in the tested permission mode (the residuals below stay open); like the `-C`/`--git-dir=` coverage above, it was verified against a stubbed `gh`: each of the ten uppercase `DELETE` forms is denied (probe G01 through probe G10), an env-prefixed form is denied (probe H1) and so is a quoted method value (probe H2). One `PUT` form and one lowercase form per position (method-first and path-first) were probed directly and are denied as well (probe G13, probe G14, probe G15, probe G16); the other `PUT` and lowercase spellings rest on the same rule text and were not each probed. The mixed-case form (e.g. `-X Delete`) is an accepted residual under literal prefix matching and remains undenied (probe G11), alongside `gh api graphql` mutations (probe H12), `gh` aliases (probe H13), and combined shorthand (e.g. `-iXDELETE`, probe H14) — this residual list is illustrative of known gaps under literal prefix matching, not exhaustive. Two broader forms are out of scope for this rule set by decision (they are scope statements, not matcher claims): `Bash(gh:*)` (the pre-existing blanket allow grant) still permits native destructive `gh` subcommands that never go through `gh api` at all — e.g. `gh repo delete` (probe H15 ran it; `gh release delete`, `gh secret set` and `gh auth token` (credential exfiltration) rest on the same blanket allow and were not probed separately: inferred, not observed) — and the still-allowed `-X PATCH` form can itself overwrite or mutate resources (probe H16; e.g. `gh api repos/o/r -X PATCH -f private=false`).
