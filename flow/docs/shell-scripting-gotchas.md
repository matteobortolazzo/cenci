# Shell scripting gotchas

Narrow, easy-to-miss pitfalls in shell/jq/grep patterns used across flow's phases,
hooks, and tests.

## Rules

- **Bash tool CWD does not reliably persist across multiple calls within a single subagent session** — an initial standalone `cd <worktree-path>` call does NOT guarantee subsequent Bash calls inherit that CWD. For verification-critical commands (test runs, build commands), especially when comparing before/after state (red vs green), always use fully absolute paths or re-verify CWD before each command, rather than relying solely on an initial `cd`. A wrong-directory execution produces a highly plausible but false result (e.g., running stale tests from the main worktree while thinking you're testing the worktree's changes). See implement skill's phase-3-test-red.md and phase-4-implement-green.md Delegation Context sections.
- In jq fallback chains for field extraction (e.g., `.field1 // .field2 // empty`), never rely on bare `//` operators to skip empty strings — jq's `//` only falls back on `null` or `false`, treating `""` as a valid truthy value. Use explicit emptiness checks: `if (.field1 // "") != "" then .field1 else (.field2 // empty) end`. This prevents empty-but-present fields (e.g., from a malformed or legacy JSON payload) from short-circuiting to unintended defaults in security guards or early-exit logic, risking silent allow-through in sensitive-file checks or other fail-closed hooks.
- **Grep-based contract tests over doc/prose text need precision on both ends of the match.** (1) When asserting a fix landed, match the specific replacement text at the edit site, never a generic marker (e.g., "git -C", "absolute path") that may already exist elsewhere in the file — generic markers pass vacuously against unfixed prose and hide regressions; see `flow/tests/subagent-cwd-contract.test.sh`'s `PHASE_3_4_5_MARKER` variable, which holds the exact replacement sentence, not a bare keyword. (2) When scanning for a retired anti-pattern's absence, a naive sweep can false-trigger on prose that *explains* why the pattern is unsafe (inline-code examples or named references that describe but don't execute it); exclude such files by exact path with a `grep -vF` filter, not a bare comment. See `flow/tests/gh-title-payload-encoding.test.sh`'s repo-wide `gh issue create` sweep (~lines 184–207), which excludes both `flow/skills/shell-rules/SKILL.md` and this very doc (`docs/shell-scripting-gotchas.md` must name the retired pattern to describe this carve-out) via `grep -vF` on their full paths — a comment alone would not have been enough. Without matching precision at both ends, the test either under-covers (vacuous pass) or over-covers (false positive on documentation).
- Wrappers over fail-closed scripts (scripts that block operations on policy violations) must distinguish genuine policy blocks from infrastructure errors when those scripts reuse the same exit code for both — the wrapper cannot check exit code alone. If the wrapped script uses exit 2 for both a genuine block AND every infra-error case (missing jq, unparseable JSON, unresolvable symlinks, etc.), grep stderr for the specific literal block-message text (e.g., `"targets the main worktree, not a feature worktree"`) to map only genuine blocks to "blocked"; all other non-zero exits map to a distinct "error" state. A wrapper that treats any non-zero exit as "blocked" silently allows broken environments to masquerade as passing "bad simulation" tests, defeating the entire harness's purpose. See `flow/tests/parity/contract-lib.sh`'s `drive_worktree_guard` and `drive_sensitive_files_guard` for the pattern.
- A bash glob substring test with an empty needle vacuously matches any content: `[[ "$haystack" == *""* ]]` always returns 0, even if `haystack` is empty. Any helper performing a required-phrase match (e.g. a contract check verifying a doc states specific mandatory text) must guard explicitly — `[[ -n "${phrase}" ]] || return 1` before the glob test — so a caller passing an unset/empty required phrase fails loudly instead of the check silently reporting a pass. See `_contains_ws_insensitive` in `flow/tests/parity/contract-lib.sh`.
- When writing shell tests that verify literal text from Markdown documentation (especially line-wrapped skill procedure docs), account for editor line-breaking: a required phrase may be split across source lines, causing a naive `grep` for the full phrase to fail even though the semantic content is correct. Extract the exact source text (preserving newlines/whitespace) into a test anchor variable before using it in grep/anchor assertions — or write the test anchor with the line-break explicitly included (e.g., `grep -q "part one\npart two"` with flags enabling multiline). See `flow/tests/parity/` for examples using `_markers_strictly_increasing` with actual doc file content (#555).
- Markdown inline-code delimiters (backticks) do not protect substrings from `grep -F` literal matching — a phrase wrapped as `` `rules`-only `` is still found by `grep -qF "rules-only"`. If line-wrapping separates backtick pairs, the intended code marker can leak as an unintended substring match in test results (e.g., a negative-assertion test expecting no "rules-only" anywhere fails when line-wrapping produces "a rules-only option" in prose text). Keep anchored phrases on single source lines in markdown docs when their content or substrings appear in grep-based contract tests.
- `flow/skills/maintain/scripts/check.sh` resolves its target repository from `pwd -P`,
  making it explicitly CWD-dependent — unlike helpers that derive paths from
  `${BASH_SOURCE[0]}`. Running it from the main checkout while intending to inspect a
  feature worktree can return a plausible result for the wrong tree; `--write` can even
  update the wrong README. For every checker call, set the shell tool working directory to the verified absolute repository or worktree path on every invocation. Never rely
  on an inherited `cd`, a relative worktree path, or a compound directory-change command.
- **Bash output redirection (`>`) creates the target file as part of shell setup, before the command executes** — even if the command fails. A pattern like `cmd > file && check_result` can mask failures because the file exists even after a non-zero exit. Checking `[[ -f file ]]` later as a success/failure signal is unreliable; an empty or truncated file may indicate either a genuine success with empty output or a failed command that never ran properly. This pitfall is especially dangerous in graceful-degrade contracts where the downstream code checks for file existence to decide whether to skip a step or emit a warning. Always pair redirection with explicit failure cleanup: `cmd > file || rm -f file`, so that `[[ -f file ]]` reliably signals success. Alternatively, capture the command's exit code separately: `cmd > file; rc=$?; [[ $rc -eq 0 ]] || { rm -f file; return $rc; }`.
- **Unchecked `cat` for config-file reads silently collapses to empty/`{}`** — when reading JSON config files or stdin, never use bare `RESULT="$(cat "$file")"` without an exit-status check. Unverified `cat` failures (unreadable file, stdin error) are silently swallowed, leaving `$RESULT` unset or empty; downstream jq/JSON processing then treats it as a missing/empty config and may drop all keys on re-write. Always guard with `if ! RESULT="$(cat "$file")"; then` followed by an error exit, or `RESULT="$(cat "$file")" || return 1`. This matches the security-critical-paths rule in root AGENTS.md and prevents silent data loss when merging config objects.
- **`chmod`-based unwritability/unreadability is a no-op for root.** uid 0 bypasses DAC permission bits, so a test that proves a script *fails* by removing permissions (`chmod 000`, `chmod a-w`, `chmod 500`) silently inverts under root: the script succeeds and the assertion false-fails, turning one environment artifact into multiple red results in `/cenci:maintain` (#642). Assertions that a script fails must use a kernel-enforced lever root cannot bypass — `ENOTDIR` (point a path component at a regular file), `EISDIR` (pre-create a directory at the target path), or `ELOOP` (pre-create a self-referential symlink). Only where the branch under test is inherently DAC-specific and unreachable by root (e.g. `[ ! -r "$f" ]`, since `access(2)` grants uid 0 read on every regular file) may a permission-removing `chmod` remain, and it must then carry an `[[ "$(id -u)" -eq 0 ]]` guard printing a visible `SKIP:` line on **stdout**. Enforced by `flow/tests/root-safe-perms-contract.test.sh`, which scans every tracked `*.test.sh` and flags a permission-removing `chmod` unless a root guard appears within the following 10 lines or a `# root-safe: <reason>` comment appears on one of the 3 preceding lines.
- When writing prose instructions for a security-hardened skill file that includes a contract test scanning for ungranted invocations (e.g., `flow/tests/design-sandbox-guard.test.sh`), example shell commands written into that prose are subject to the same least-privilege grant-set constraints as the skill's own implementation — a plausible-looking verification command like `git status --short` or `git diff --cached --name-only` can silently violate the very grant set the ticket is narrowing if it isn't in the `allowed-tools` list. Substitute a CLI-agnostic check (e.g., Glob/Read-based file-existence verification) instead of adding a new grant entry to accommodate the example. This recurs across least-privilege skill-narrowing tickets (#738, #740, #749, #773).
- **An `mktemp`-failure fallback must never assign `/dev/null` to a path later passed to `rm`, and must not swallow the diagnostic it was meant to carry.** The tempting one-liner `JQ_ERR=$(mktemp 2>/dev/null) || JQ_ERR=/dev/null` looks safe but has two independent defects: (1) every later unconditional `rm -f "$JQ_ERR"` unlinks `/dev/null` itself when run as root, since root's DAC bypass makes the device node just another unlinkable path; (2) redirecting the wrapped command's stderr into `/dev/null` permanently discards its diagnostic — `$(cat "$JQ_ERR")` then interpolates an empty string, so the operator sees `failed to parse <config>: ` with no cause, and a guarded-`rm` fix alone does not restore that lost text. The fix is the fd-9 indirection pattern (`flow/hooks/scripts/{guard-main-worktree,check-sensitive-files,run-gate,resolve-babysit-interval}.sh`, #550): on `mktemp` success, `exec 9>"$JQ_ERR"` and route every subsequent call's stderr through `2>&9`; on failure, never assign `/dev/null` — set `JQ_ERR=""`, `exec 9>&2` (fd 9 becomes a direct passthrough to the script's own stderr), and print a warning that jq's errors follow on stderr directly. A `jq_err_detail()` helper prints the captured file's content when one exists, else a literal pointer to the passthrough output already printed; a `jq_err_cleanup()` helper closes fd 9 and removes the temp file only when `$JQ_ERR` is non-empty. Because `/dev/null` is never assigned, no `rm` call anywhere in the script can ever target it — there is no guard to remember at each call site. If the script later `exec`s a child process (e.g. `run-gate.sh`'s `gateCommand`), `jq_err_cleanup` must run before that exec, or the child inherits the open fd 9 write handle.
- **A shell function's return code is the exit status of its last executed command — if that last command is a conditional test-and-act idiom (`[ cond ] && action`), the function silently reports failure when the condition is false, even though nothing failed.** This is insidious in cleanup functions (`jq_err_cleanup`, temp-file unlink helpers): the pattern `[ -n "$VAR" ] && rm -f "$VAR"` returns 1 when `$VAR` is empty (the "nothing to clean up" success case), causing the function to return 1. Today it may be harmless (no `set -e`, all call sites followed by explicit `exit`), but if `set -e` is ever added to a fail-closed security guard, the cleanup function's silent return-1 aborts the guard at the wrong point — and since Claude Code treats a hook's exit 1 as non-blocking, the write that should be blocked proceeds instead. The fix: rewrite cleanup using an explicit `if` statement with an unconditional command at the end:
  ```sh
  jq_err_cleanup() {
    exec 9>&-
    if [ -n "$JQ_ERR" ]; then
      rm -f "$JQ_ERR"
    fi
  }
  ```
  The function's return status is now the `fi` statement itself (success), regardless of whether the `rm` executed. Apply this rule to any helper function that performs conditional resource cleanup or rollback, not just temp files.
- When narrowing or dropping a Bash grant from a skill's `allowed-tools` (e.g., removing `Bash(mkdir:*)` or `Bash(rm:*)`), grep the *entire* skill file — not just re-reading identified edit sites — for prose references to the removed tool or capability. Stale references can survive in unrelated sections (e.g., a "Hard gate" security description 130 lines below the frontmatter) when re-read guidance is narrowly scoped to only files with many edit locations. Always run a full-file search for each removed tool name when any grant is dropped, regardless of how many locations were edited (#740, #773).
- **Path-containment security checks (comparing two filesystem paths, or canonicalizing a leaf against an allowed root) have independent, complementary escape vectors — test and guard each one.** (1) Directional asymmetry: a guard that only rejects when path A is an ancestor of path B silently widens access if B is instead an ancestor of A — e.g. a `TMPDIR_ALLOW` guard rejecting `TMPDIR == $ROOT` and `TMPDIR` ancestor-of `$ROOT` can still allow writes to `$ROOT/tmp` when `TMPDIR=$ROOT/tmp` (the descendant case). Add explicit tests for all three cases (equality, A ancestor of B, B ancestor of A). See `flow/hooks/scripts/guard-main-worktree.sh` (#749). (2) Leaf symlinks: a check that canonicalizes only the parent directory (`cd "$(dirname "$path")" && pwd -P`) and re-appends the leaf's `basename` never detects a symlink at the leaf itself — a symlink literally named `AGENTS.md` pointing outside the intended root still string-concatenates back to a path under the root, so the containment check passes even though the later `-f`/`awk`/`grep` read transparently follows the link out of bounds. Reject the leaf explicitly with `[[ ! -L "$path" ]] || return 1` before/alongside directory canonicalization — additive to, not a replacement for, the ancestor-directory check, since the two guard different escape vectors. Before writing a new path-safety helper, grep for an existing one first: `canonicalize_dir_allow_missing()` in `flow/skills/maintain/scripts/check.sh` already implements the `[[ ! -L ]]` leaf-rejection pattern, but a sibling helper (`context_budget_path_safe()`) was added without reusing or even checking it — the omission surfaced only on a second, independent review pass (#753).
- **Test helpers making negative assertions (e.g., `assert_file_lacks`, "must NOT contain") must guard for file existence before checking content.** Without an `[[ -f "$1" ]]` guard before the grep check, the assertion silently passes if the file is missing or renamed, vacuously satisfying a claim that is actually meaningless ("a 'must not contain' claim about a nonexistent file is meaningless and must never pass"). This is especially important for helpers that are reused across multiple test files, where a file rename or deletion elsewhere in the codebase can create a false pass. Compare `flow/tests/maintain.test.sh`'s documented `assert_file_lacks_phrase` pattern.
- **When extracting markdown sections with awk (e.g., `awk '/^## Section/ { on=1 } on { print }'`), account for code fences that may contain literal section-marker text** — use a toggle flag to track fence state (`/^```/ { infence = !infence }`) and only treat `^## ` as a real section boundary when `!infence`. A naive boundary check that doesn't account for fences falsely matches literal text inside code blocks (e.g., a fenced code block showing an example like `## Ticket Details`), causing over-capture or wrong extraction. This pitfall especially recurs when extracting from front-matter template blocks that show example markdown structures. See `flow/tests/plan-persist-sections-contract.test.sh`'s `extract_persist_section` pattern: toggle fence state and guard the boundary condition with `!infence` before accepting a section-end match (#782).
- **Never call `fail()` or any counter/state-modifying function directly from within a function invoked via command substitution (`RESULT=$(helper_that_calls_fail "$arg")`)**, because the subshell's state changes (counter increments, array assignments) are lost in the parent shell. A `fail()` call from inside a command substitution subshell silently drops the failure count, causing the script to report `failures=0` even when errors occurred. Structure helpers as pure extractors (no side effects) invoked inside `$(...)`, then wrap them in a caller that checks the result and calls `fail()` in the parent shell (see the `require_first_line` / `first_line_of` pattern in `flow/tests/plan-persist-sections-contract.test.sh:163-190`). A helper that calls `fail()` cannot be invoked via command substitution — either restructure it to be a pure extractor, or invoke it without command substitution and handle its return code explicitly in the parent shell (#782). Enforced by `flow/tests/read-helper-purity-contract.test.sh`, which scans every tracked `*.test.sh` file plus every tracked `*.sh` shell library under `flow/tests/` (sourced harness libraries such as `flow/tests/parity/contract-lib.sh`, whose helpers run in the sourcing suite's shell) for a `read_*`-named function whose body calls `fail()`, keying on the `<name>_raw` (pure extractor) + `require_<name>` (nameref wrapper) naming convention every swept helper pair follows (#797, #791).
- **SessionStart hook payloads must be built with `jq -n --arg`, never heredoc/string interpolation.** A `cat <<EOF` heredoc that interpolates an externally-sourced value (e.g. a filename read from a repo directory) directly into a JSON string produces malformed JSON on a `"`, `\`, or embedded newline, or — worse — lets that value's content masquerade as trusted context once parsed. Build the human-readable message in a shell variable, then hand the whole string to jq once: `jq -n --arg ctx "$CTX" '{hookSpecificOutput:{hookEventName:"SessionStart",additionalContext:$ctx}}'`. Names sourced from outside the script's own control (filenames, directory listings) must also be enumerated NUL-safely — `find ... -print0` piped through `LC_ALL=C sort -z` into `while IFS= read -r -d ''` — never newline-joined/`wc -l`-counted iteration, which one embedded newline in a name can silently corrupt. Such names must additionally be control-character-filtered (`case "$name" in *[[:cntrl:]]*) ... ;; esac` under `LC_ALL=C`) before entering the payload — excluded, not sanitized, since a mangled name can break a resume instruction the payload itself issues. See `flow/hooks/scripts/check-pending-plans.sh` (#784).
- **Diagnostic/advisory hints inside untrusted-data-handling code must themselves be byte-safe — they are a secondary injection vector if the hint tells the user how to reproduce the unsafe bytes.** When advice text tells a user/operator how to "fix" excluded unsafe data by running a command (e.g., "rename them (see `ls .plans/`)" in a pending-plans hook), that command's output becomes part of the message corpus and can reintroduce control/escape bytes into the transcript. The hint itself is trusted context once it enters the payload, so it must match the primary payload's sanitization level. Plain `ls` piped to non-tty does not escape control bytes; always use `ls -b` or equivalent byte-safe output modes when advisory text references file-enumeration commands that will be visible to the user. The exception is when the hint is prose-only (no suggestion to run a command) — generic advice like "unsafe names were excluded" is safe without escaping, but "see `ls .plans/`" must use `ls -b` to avoid reintroducing the bytes the script had just filtered. See `flow/hooks/scripts/check-pending-plans.sh` line 124 (#784).
- **Claude Code allow-rule prefix matching is literal-prefix, and only a trailing `:*` — never a bare `*` — turns the suffix into a wildcard.** A command whose invariant tokens are separated by a varying value in the middle (e.g. `git -C <worktree-path> <verb>`, where `<worktree-path>` differs per call) cannot be scoped down to the verb; the tightest expressible grant collapses to the shared literal prefix before the first variable segment, e.g. `Bash(git -C:*)` — near-equivalent to `Bash(git:*)` for any skill that also needs several `git -C ...` call sites. Separately, a bare `*` with no colon is treated as a literal character, not a wildcard: the malformed grant `Bash(rm -f ${TMPDIR:-/tmp}/cenci/cenci-configure-*)` does not match invocations like `rm -f ${TMPDIR:-/tmp}/cenci/cenci-configure-<slug>-pr-body.md`; it must be `Bash(rm -f ${TMPDIR:-/tmp}/cenci/cenci-configure-:*)` to prefix-match all such variants. Both failure modes are fail-safe, not silent escapes: a grant string that doesn't literal-prefix-match a real invocation (e.g. because of unexpected `${VAR}` expansion or a missing `:*`) causes a client approval prompt, never an unintended pass-through — document this limitation once per swept skill rather than trying to widen the grant further. Contract tests that verify set-equality between a skill's frontmatter `allowed-tools` and an `EXPECTED_*_GRANTS` constant (e.g., `allowed-tools-sweep.test.sh`) cannot catch a `:*`-omission when both sides omit it identically — the test passes vacuously because both strings match each other; always manually verify a new grant pattern against a real command invocation (or test it in Claude Code directly) before finalizing, especially when the grant contains a variable segment (#773).
- **An invocation-vs-grant scan (a `case`/regex sweep matching every `git`/`gh`/etc. token actually invoked in a skill's fenced code blocks against its `allowed-tools` grant list) must be scoped to fenced code blocks, or the whole file must be skipped, when the file's prose legitimately enumerates commands as data rather than as invocations this skill's own agent turn issues.** A whole-file token scan produces two distinct false-positive classes: (1) inline single-backtick prose that merely *mentions* a command (e.g. "extract owner/repo from `git remote get-url origin`") rather than fencing it as an executable block, and (2) a skill that documents another surface's command set as literal data — e.g. `configure/SKILL.md`'s `permissions.deny` section, which lists dozens of `git ...` strings as the *generated project's* deny-list entries, and its settings-template callout, which lists `Bash(git:*)`/`Bash(gh:*)` as *that template's* base permissions — neither is an invocation this skill's own Bash calls make. Restrict invocation-vs-grant scans to fenced ` ```bash ` blocks (see `extract_bash_fences` in `flow/tests/allowed-tools-sweep.test.sh`), and exempt a file entirely, with an explicit filename carve-out and comment, when its prose enumerates commands as data throughout rather than at one isolated site (#773).
- **When writing a line-by-line state-machine scanner in a contract test that transitions into a scoped context (e.g., entering "in-function" scope on a function-definition regex match), check the line that triggers the state transition for the condition you're scanning — don't assume the trigger line itself is inert.** A single-line function definition like `read_doc() { fail "..."; }` will silently escape detection if the state-machine logic unconditionally continues to the next line without first checking the definition line itself for condition matches (e.g., a same-line closing brace and `fail()` call). Multi-line transitions are correctly scanned only because the next-line check finds the closing brace; single-line ones bypass that next-line check entirely, leaving a latent gap in scanner coverage. See `flow/tests/read-helper-purity-contract.test.sh` for the corrected pattern: check the definition line before advancing state, then check subsequent lines normally (#797).
- **Process substitution for input (`< <(cmd)`) hides the underlying command's exit status from the caller** — if cmd fails, the reader reaches EOF but never sees the failure, making it indistinguishable from a command that succeeds with empty output. For enumeration helpers (git ls-files, find) or any command where exit-status observability is critical, route through an explicitly-checked temp file: `cmd > "$tmpfile" || return 1`, then `< "$tmpfile"`. Never invoke an enumeration helper via `< <(helper ...)` if its `return 1` (e.g., on mktemp failure) must be observable to the caller; the process-substitution indirection loses the exit code silently. This pattern is enforced by `flow/tests/read-helper-purity-contract.test.sh` (#791).
- **A hook command must never begin with a PATH-resolved interpreter or bare-word program — Codex runs hooks through a *login* shell, whose PATH omits version-manager tooling.** `codex-rs/hooks/src/engine/command_runner.rs`'s `default_shell_command` executes every hook as `$SHELL -lc "<command>"`. A login shell sources `~/.profile` but **not** `~/.bashrc`, and nvm/fnm/mise/volta all initialize in `~/.bashrc` — so `node`, `python`, `uv`, etc. are simply absent from a hook's PATH on a developer machine where they work fine interactively. The failure is maximally confusing: the hook dies with `hook exited with code 127` before a single line of cenci code runs, so it reads as a cenci bug rather than a PATH one, and it strikes only the events whose command carries the interpreter prefix (flow's `SessionStart`/`PreCompact`/`Stop` died via `node "${PLUGIN_ROOT}/codex/hook-output.mjs"` while the `PreToolUse` guards, which invoke their `.sh` files directly, kept working — making it look like "start/stop hooks are broken"). Write every hook command as a direct `"${PLUGIN_ROOT}/..."`-anchored executable with a `#!/bin/sh` shebang, and keep the hook path's dependencies to what a bare login shell guarantees. Note the asymmetry with `${PLUGIN_ROOT}` itself, which is safe: Codex string-substitutes it into the command *before* the shell ever sees it (`engine/discovery.rs`), and additionally exports it — but only for plugin-bundled hook sources, never config-layer ones (`env: HashMap::new()`). Where a payload genuinely needs a tool (e.g. `jq` for the SessionStart envelope), degrade to a valid empty payload plus a stderr warning and `exit 0` rather than propagating a non-zero exit — an advisory hook must never be why a session fails to start. Enforced by `flow/codex/hooks.test.sh`, which asserts every command in `codex/hooks.json` starts with a quoted `${PLUGIN_ROOT}` path *and* executes each one with `node` masked to exit 127.
