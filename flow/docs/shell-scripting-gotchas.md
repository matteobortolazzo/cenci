# Shell scripting gotchas

Narrow, easy-to-miss pitfalls in shell/jq/grep patterns used across flow's phases,
hooks, and tests.

## Rules

- **Bash tool CWD does not reliably persist across multiple calls within a single subagent session** — an initial standalone `cd <worktree-path>` call does NOT guarantee subsequent Bash calls inherit that CWD. For verification-critical commands (test runs, build commands, `flow/skills/maintain/scripts/check.sh`), especially when comparing before/after state (red vs green), always use fully absolute paths or re-verify CWD before each command, rather than relying solely on an initial `cd`. A wrong-directory execution produces a highly plausible but false result (e.g., running stale tests from the main worktree while thinking you're testing the worktree's changes). `check.sh` specifically resolves its target repository from `pwd -P` — unlike helpers that derive paths from `${BASH_SOURCE[0]}` — so running it from the main checkout while intending to inspect a feature worktree can return a plausible result for the wrong tree; `--write` can even update the wrong README. For every checker call, set the shell tool working directory to the verified absolute repository or worktree path on every invocation — never rely on an inherited `cd`, a relative worktree path, or a compound directory-change command. See implement skill's phase-3-test-red.md and phase-4-implement-green.md Delegation Context sections.
- In jq fallback chains for field extraction (e.g., `.field1 // .field2 // empty`), never rely on bare `//` operators to skip empty strings — jq's `//` only falls back on `null` or `false`, treating `""` as a valid truthy value. Use explicit emptiness checks: `if (.field1 // "") != "" then .field1 else (.field2 // empty) end`. This prevents empty-but-present fields (e.g., from a malformed or legacy JSON payload) from short-circuiting to unintended defaults in security guards or early-exit logic, risking silent allow-through in sensitive-file checks or other fail-closed hooks.
- **Grep-based contract tests over doc/prose text need precision on both ends of the match.** (1) When asserting a fix landed, match the specific replacement text at the edit site, never a generic marker (e.g., "git -C", "absolute path") that may already exist elsewhere in the file — generic markers pass vacuously against unfixed prose and hide regressions; see `flow/tests/subagent-cwd-contract.test.sh`'s `PHASE_3_4_5_MARKER` variable, which holds the exact replacement sentence, not a bare keyword. (2) When scanning for a retired anti-pattern's absence, a naive sweep can false-trigger on prose that *explains* why the pattern is unsafe (inline-code examples or named references that describe but don't execute it); exclude such files by exact path with a `grep -vF` filter, not a bare comment. See `flow/tests/gh-title-payload-encoding.test.sh`'s repo-wide `gh issue create` sweep (~lines 184–207), which excludes both `flow/skills/shell-rules/SKILL.md` and this very doc (`docs/shell-scripting-gotchas.md` must name the retired pattern to describe this carve-out) via `grep -vF` on their full paths — a comment alone would not have been enough. (3) When a test extracts one specific occurrence from `grep` output via `tail` or similar filtering, the extraction must be preceded by a scoped search, not a whole-file search: a naive `grep <pattern> <file> | tail -1` passes vacuously when the pattern matches multiple lines, since `tail` blindly picks the *last* match across the entire file rather than the specific occurrence the test was meant to guard — if that last match is unrelated prose (e.g., an inline code example from a "How to write safe scripts" section), the test passes even when the real intended marker, in a specific procedure section, is malformed. Narrow the search first (`sed -n '<start>,<end>p'` or `awk`/`head -n +<line>`) to extract only the relevant section, then apply the grep pattern within that narrowed scope, and pair every such multi-match test with a non-vacuity injection that deliberately breaks the real marker and verifies the test catches it (#957). Without matching precision at all three points, the test either under-covers (vacuous pass) or over-covers (false positive on documentation).
- Wrappers over fail-closed scripts (scripts that block operations on policy violations) must distinguish genuine policy blocks from infrastructure errors when those scripts reuse the same exit code for both — the wrapper cannot check exit code alone. If the wrapped script uses exit 2 for both a genuine block AND every infra-error case (missing jq, unparseable JSON, unresolvable symlinks, etc.), grep stderr for the specific literal block-message text (e.g., `"targets the main worktree, not a feature worktree"`) to map only genuine blocks to "blocked"; all other non-zero exits map to a distinct "error" state. A wrapper that treats any non-zero exit as "blocked" silently allows broken environments to masquerade as passing "bad simulation" tests, defeating the entire harness's purpose. See `flow/tests/parity/contract-lib.sh`'s `drive_worktree_guard` and `drive_sensitive_files_guard` for the pattern.
- A bash glob substring test with an empty needle vacuously matches any content: `[[ "$haystack" == *""* ]]` always returns 0, even if `haystack` is empty. Any helper performing a required-phrase match (e.g. a contract check verifying a doc states specific mandatory text) must guard explicitly — `[[ -n "${phrase}" ]] || return 1` before the glob test — so a caller passing an unset/empty required phrase fails loudly instead of the check silently reporting a pass. See `_contains_ws_insensitive` in `flow/tests/parity/contract-lib.sh`.
- **Line-wrapping in Markdown source breaks grep-based contract tests in two complementary directions — false negative and false positive.** (1) False negative: a required phrase split across source lines by editor line-breaking makes a naive `grep` for the full phrase fail even though the semantic content is correct. Extract the exact source text (preserving newlines/whitespace) into a test anchor variable before using it in grep/anchor assertions — or write the test anchor with the line-break explicitly included (e.g., `grep -q "part one\npart two"` with flags enabling multiline). See `flow/tests/parity/` for examples using `_markers_strictly_increasing` with actual doc file content (#555). (2) False positive: inline-code delimiters (backticks) do not protect substrings from `grep -F` literal matching — a phrase wrapped as `` `rules`-only `` is still found by `grep -qF "rules-only"`, so when line-wrapping separates backtick pairs the intended code marker leaks as an unintended substring match (e.g., a negative-assertion test expecting no "rules-only" anywhere fails when line-wrapping produces "a rules-only option" in prose text). Both directions have the same mitigation on the doc side: keep anchored phrases on single source lines in markdown docs when their content or substrings appear in grep-based contract tests.
- **Shell redirection and process substitution can each silently hide a command's failure exit status, in complementary ways.** (1) Output redirection (`>`) creates the target file as part of shell setup, before the command executes — even if the command fails. A pattern like `cmd > file && check_result` can mask failures because the file exists even after a non-zero exit. Checking `[[ -f file ]]` later as a success/failure signal is unreliable; an empty or truncated file may indicate either a genuine success with empty output or a failed command that never ran properly. This pitfall is especially dangerous in graceful-degrade contracts where the downstream code checks for file existence to decide whether to skip a step or emit a warning. Always pair redirection with explicit failure cleanup: `cmd > file || rm -f file`, so that `[[ -f file ]]` reliably signals success. Alternatively, capture the command's exit code separately: `cmd > file; rc=$?; [[ $rc -eq 0 ]] || { rm -f file; return $rc; }`. (2) Process substitution for input (`< <(cmd)`) hides the underlying command's exit status from the caller in the opposite direction — if cmd fails, the reader reaches EOF but never sees the failure, making it indistinguishable from a command that succeeds with empty output. For enumeration helpers (git ls-files, find) or any command where exit-status observability is critical, route through an explicitly-checked temp file: `cmd > "$tmpfile" || return 1`, then `< "$tmpfile"`. Never invoke an enumeration helper via `< <(helper ...)` if its `return 1` (e.g., on mktemp failure) must be observable to the caller; the process-substitution indirection loses the exit code silently. This pattern is enforced by `flow/tests/read-helper-purity-contract.test.sh` (#791).
- **`chmod`-based unwritability/unreadability is a no-op for root.** uid 0 bypasses DAC permission bits, so a test that proves a script *fails* by removing permissions (`chmod 000`, `chmod a-w`, `chmod 500`) silently inverts under root: the script succeeds and the assertion false-fails, turning one environment artifact into multiple red results in `/cenci:maintain` (#642). Assertions that a script fails must use a kernel-enforced lever root cannot bypass — `ENOTDIR` (point a path component at a regular file), `EISDIR` (pre-create a directory at the target path), or `ELOOP` (pre-create a self-referential symlink). Only where the branch under test is inherently DAC-specific and unreachable by root (e.g. `[ ! -r "$f" ]`, since `access(2)` grants uid 0 read on every regular file) may a permission-removing `chmod` remain, and it must then carry an `[[ "$(id -u)" -eq 0 ]]` guard printing a visible `SKIP:` line on **stdout**. Enforced by `flow/tests/root-safe-perms-contract.test.sh`, which scans every tracked `*.test.sh` and flags a permission-removing `chmod` unless a root guard appears within the following 10 lines or a `# root-safe: <reason>` comment appears on one of the 3 preceding lines.
- **`allowed-tools` grant contracts (#738, #740, #749, #773) have four independent pitfalls — one in authoring prose examples, one in sweeping for stale references after narrowing a grant, and two in how a grant string itself is authored and swept for.** (1) When writing prose instructions for a security-hardened skill file that includes a contract test scanning for ungranted invocations (e.g., `flow/tests/design-sandbox-guard.test.sh`), example shell commands written into that prose are subject to the same least-privilege grant-set constraints as the skill's own implementation — a plausible-looking verification command like `git status --short` or `git diff --cached --name-only` can silently violate the very grant set the ticket is narrowing if it isn't in the `allowed-tools` list. Substitute a CLI-agnostic check (e.g., Glob/Read-based file-existence verification) instead of adding a new grant entry to accommodate the example. This recurs across least-privilege skill-narrowing tickets (#738, #740, #749, #773). (2) When narrowing or dropping a Bash grant from a skill's `allowed-tools` (e.g., removing `Bash(mkdir:*)` or `Bash(rm:*)`), grep the *entire* skill file — not just re-reading identified edit sites — for prose references to the removed tool or capability. Stale references can survive in unrelated sections (e.g., a "Hard gate" security description 130 lines below the frontmatter) when re-read guidance is narrowly scoped to only files with many edit locations. Always run a full-file search for each removed tool name when any grant is dropped, regardless of how many locations were edited (#740, #773). (3) Claude Code allow-rule prefix matching is literal-prefix, and only a trailing `:*` — never a bare `*` — turns the suffix into a wildcard. A command whose invariant tokens are separated by a varying value in the middle (e.g. `git -C <worktree-path> <verb>`) cannot be scoped down to the verb; the tightest expressible grant collapses to the shared literal prefix before the first variable segment, e.g. `Bash(git -C:*)` — near-equivalent to `Bash(git:*)`. Separately, a bare `*` with no colon is a literal character, not a wildcard: `Bash(rm -f ${TMPDIR:-/tmp}/cenci/cenci-configure-*)` does not match `rm -f ${TMPDIR:-/tmp}/cenci/cenci-configure-<slug>-pr-body.md`; it must be `Bash(rm -f ${TMPDIR:-/tmp}/cenci/cenci-configure-:*)`. Both failure modes are fail-safe, not silent escapes — a non-matching grant causes a client approval prompt, never an unintended pass-through — but a set-equality contract test (e.g. `allowed-tools-sweep.test.sh`) cannot catch a `:*`-omission when both sides omit it identically, so always manually verify a new grant pattern against a real invocation before finalizing. (4) An invocation-vs-grant scan (a `case`/regex sweep matching every `git`/`gh`/etc. token actually invoked in a skill's fenced code blocks against its `allowed-tools` list) must be scoped to fenced code blocks, or the whole file skipped, when the file's prose legitimately enumerates commands as data rather than as invocations this skill's own agent turn issues — e.g. inline single-backtick prose that merely *mentions* a command, or a skill documenting another surface's command set as literal data (`configure/SKILL.md`'s `permissions.deny` section lists the *generated project's* deny-list entries, not this skill's own invocations). Restrict scans to fenced ` ```bash ` blocks (see `extract_bash_fences` in `flow/tests/allowed-tools-sweep.test.sh`), and exempt a file entirely, with an explicit filename carve-out, when its prose enumerates commands as data throughout.
- **The `jq_err_cleanup` fd-9 indirection pattern (`flow/hooks/scripts/{guard-main-worktree,check-sensitive-files,run-gate,resolve-babysit-interval}.sh`, #550) has two independent correctness traps.** (1) An `mktemp`-failure fallback must never assign `/dev/null` to a path later passed to `rm`, and must not swallow the diagnostic it was meant to carry: the tempting one-liner `JQ_ERR=$(mktemp 2>/dev/null) || JQ_ERR=/dev/null` looks safe but every later unconditional `rm -f "$JQ_ERR"` unlinks `/dev/null` itself when run as root (DAC bypass makes the device node just another unlinkable path), and redirecting the wrapped command's stderr into `/dev/null` permanently discards its diagnostic — `$(cat "$JQ_ERR")` then interpolates an empty string, so the operator sees `failed to parse <config>: ` with no cause. On `mktemp` success, `exec 9>"$JQ_ERR"` and route every subsequent call's stderr through `2>&9`; on failure, never assign `/dev/null` — set `JQ_ERR=""`, `exec 9>&2` (fd 9 becomes a direct passthrough), and print a warning that jq's errors follow on stderr directly. A `jq_err_detail()` helper prints the captured file's content when one exists, else a pointer to the passthrough output already printed; run `jq_err_cleanup` before any later `exec` of a child process (e.g. `run-gate.sh`'s `gateCommand`), or the child inherits the open fd 9 write handle. (2) A shell function's return code is the exit status of its last executed command — if that last command is a conditional test-and-act idiom (`[ cond ] && action`), the function silently reports failure when the condition is false, even though nothing failed. The naive `jq_err_cleanup` body `[ -n "$JQ_ERR" ] && rm -f "$JQ_ERR"` returns 1 when `$JQ_ERR` is empty (the "nothing to clean up" success case); harmless today (no `set -e`, call sites followed by explicit `exit`), but if `set -e` is ever added to a fail-closed security guard, the silent return-1 aborts the guard at the wrong point, and since Claude Code treats a hook's exit 1 as non-blocking, the write that should be blocked proceeds instead. Rewrite as an explicit `if` with an unconditional trailing statement:
  ```sh
  jq_err_cleanup() {
    exec 9>&-
    if [ -n "$JQ_ERR" ]; then
      rm -f "$JQ_ERR"
    fi
  }
  ```
  Apply this to any helper performing conditional resource cleanup or rollback, not just temp files.
- **Path-containment security checks (comparing two filesystem paths, or canonicalizing a leaf against an allowed root) have independent, complementary escape vectors — test and guard each one.** (1) Directional asymmetry: a guard that only rejects when path A is an ancestor of path B silently widens access if B is instead an ancestor of A — e.g. a `TMPDIR_ALLOW` guard rejecting `TMPDIR == $ROOT` and `TMPDIR` ancestor-of `$ROOT` can still allow writes to `$ROOT/tmp` when `TMPDIR=$ROOT/tmp` (the descendant case). Add explicit tests for all three cases (equality, A ancestor of B, B ancestor of A). See `flow/hooks/scripts/guard-main-worktree.sh` (#749). (2) Leaf symlinks: a check that canonicalizes only the parent directory (`cd "$(dirname "$path")" && pwd -P`) and re-appends the leaf's `basename` never detects a symlink at the leaf itself — a symlink literally named `AGENTS.md` pointing outside the intended root still string-concatenates back to a path under the root, so the containment check passes even though the later `-f`/`awk`/`grep` read transparently follows the link out of bounds. Reject the leaf explicitly with `[[ ! -L "$path" ]] || return 1` before/alongside directory canonicalization — additive to, not a replacement for, the ancestor-directory check, since the two guard different escape vectors. Before writing a new path-safety helper, grep for an existing one first: `canonicalize_dir_allow_missing()` in `flow/skills/maintain/scripts/check.sh` already implements the `[[ ! -L ]]` leaf-rejection pattern, but a sibling helper (`context_budget_path_safe()`) was added without reusing or even checking it — the omission surfaced only on a second, independent review pass (#753).
- **Test helpers making negative assertions (e.g., `assert_file_lacks`, "must NOT contain") must guard for file existence before checking content.** Without an `[[ -f "$1" ]]` guard before the grep check, the assertion silently passes if the file is missing or renamed, vacuously satisfying a claim that is actually meaningless ("a 'must not contain' claim about a nonexistent file is meaningless and must never pass"). This is especially important for helpers that are reused across multiple test files, where a file rename or deletion elsewhere in the codebase can create a false pass. Compare `flow/tests/maintain.test.sh`'s documented `assert_file_lacks_phrase` pattern.
- **Awk-based markdown section-boundary extraction has two independent fragility modes — code fences and phrase-heuristic line-wrapping — and each needs its own guard plus a non-vacuity self-test.** (1) Fences: a naive `awk '/^## Section/ { on=1 } on { print }'` falsely matches literal section-marker text inside a fenced code block (e.g. an example showing `## Ticket Details`), causing over-capture; track fence state with a toggle (`/^```/ { infence = !infence }`) and only treat `^## ` as a real boundary when `!infence`. This especially recurs when extracting from front-matter template blocks that show example markdown structures. See `flow/tests/plan-persist-sections-contract.test.sh`'s `extract_persist_section` pattern (#782). (2) Phrase heuristics: a boundary check that requires multiple words/phrases on the same physical source line (e.g. "stop at first line containing 'Gate' but not 'above'/'below' on the same line") breaks when Markdown line-wrapping soft-wraps one of those words onto the next line (e.g. "... at the `## Confirmation Gate` below" splitting across lines), causing the extractor to exit at the wrong place and silently narrow its scan window by tens of lines; anchor on a literal boundary instead — the exact heading line (`awk '/^## Confirmation Gate$/'`) or an exact substring (`awk ... index($0, "**Exact Marker Text**")`) — never a phrase-presence heuristic with exclusions. See `flow/tests/refine-write-order.test.sh` lines 310–359 (#878). Both modes share the same proof discipline: pair every such extractor with a non-vacuity self-test (distinct from the real doc's accuracy test) that injects a synthetic violation into a deliberately-broken `mktemp -d` copy of the doc and proves the extractor catches it — if boundary logic or format assumptions fail silently on the real doc, the injected test will fail loudly.
- **Self-test harnesses for fail-closed regression tests (e.g. `flow/tests/read-helper-purity-contract.test.sh`) have three related `fail()`-call correctness traps.** (1) Never call `fail()` or any counter/state-modifying function directly from within a function invoked via command substitution (`RESULT=$(helper_that_calls_fail "$arg")`) — the subshell's state changes (counter increments, array assignments) are lost in the parent shell, silently dropping the failure count so the script reports `failures=0` even when errors occurred. Structure helpers as pure extractors (no side effects) invoked inside `$(...)`, then wrap them in a caller that checks the result and calls `fail()` in the parent shell (see the `require_first_line`/`first_line_of` pattern in `flow/tests/plan-persist-sections-contract.test.sh:163-190`); a helper that calls `fail()` cannot be invoked via command substitution (#782). (2) A helper asserting a failure counter incremented by exactly N (e.g. `expect_one_failure`) cannot distinguish between multiple code paths that increment the counter — if the code under test can increment it via more than one path, a delta-only assertion is ambiguous and becomes a vacuous tautology. Verify by explicit code inspection that ONLY the intended path increments the counter, or inject the exact regression the test exists to prevent and confirm the test still fails; pair every counter-delta assertion with this non-vacuity proof (#812). (3) In a regression test verifying a fail-closed operation fails correctly, the `fail()` call must live ONLY on the "regression detected" branch, never on the "behavior is correct" branch — if both branches can call `fail()`, the test cannot distinguish a caught regression from an uncaught one; structure the test so only the regression-detection branch calls `fail()`, with the success branch silently passing or using a distinct success-assertion function. Enforced by `flow/tests/read-helper-purity-contract.test.sh`, which scans every tracked `*.test.sh` file plus every tracked `*.sh` shell library under `flow/tests/` (sourced harness libraries such as `flow/tests/parity/contract-lib.sh`, whose helpers run in the sourcing suite's shell) for a `read_*`-named function whose body calls `fail()`, keying on the `<name>_raw`/`require_<name>` naming convention every swept helper pair follows (#797, #791, #812).
- **All text entering a SessionStart hook JSON payload — both the primary message and any embedded advisory hints — must be built with `jq -n --arg` and sanitized to the same byte-safety standard, never via heredoc/string interpolation.** A `cat <<EOF` heredoc that interpolates an externally-sourced value (e.g. a filename read from a repo directory) directly into a JSON string produces malformed JSON on a `"`, `\`, or embedded newline, or — worse — lets that value's content masquerade as trusted context once parsed. Build the human-readable message in a shell variable, then hand the whole string to jq once: `jq -n --arg ctx "$CTX" '{hookSpecificOutput:{hookEventName:"SessionStart",additionalContext:$ctx}}'`. Names sourced from outside the script's own control (filenames, directory listings) must also be enumerated NUL-safely — `find ... -print0` piped through `LC_ALL=C sort -z` into `while IFS= read -r -d ''` — never newline-joined/`wc -l`-counted iteration, which one embedded newline in a name can silently corrupt — and control-character-filtered (`case "$name" in *[[:cntrl:]]*) ... ;; esac` under `LC_ALL=C`) before entering the payload, excluded rather than sanitized, since a mangled name can break a resume instruction the payload itself issues. Diagnostic/advisory hints are a secondary injection vector if the hint tells the user how to reproduce the unsafe bytes: when advice text tells a user/operator how to "fix" excluded unsafe data by running a command (e.g., "rename them (see `ls .plans/`)"), that command's output becomes part of the message corpus and can reintroduce control/escape bytes into the transcript, so it must match the primary payload's sanitization level — plain `ls` piped to non-tty does not escape control bytes, so always use `ls -b` or an equivalent byte-safe output mode when advisory text references a file-enumeration command that will be visible to the user. The exception is a prose-only hint with no suggested command — generic advice like "unsafe names were excluded" is safe without escaping. See `flow/hooks/scripts/check-pending-plans.sh` (the `UNSAFE_COUNT` advisory branch) (#784).
- **When writing a line-by-line state-machine scanner in a contract test that transitions into a scoped context (e.g., entering "in-function" scope on a function-definition regex match), check the line that triggers the state transition for the condition you're scanning — don't assume the trigger line itself is inert.** A single-line function definition like `read_doc() { fail "..."; }` will silently escape detection if the state-machine logic unconditionally continues to the next line without first checking the definition line itself for condition matches (e.g., a same-line closing brace and `fail()` call). Multi-line transitions are correctly scanned only because the next-line check finds the closing brace; single-line ones bypass that next-line check entirely, leaving a latent gap in scanner coverage. See `flow/tests/read-helper-purity-contract.test.sh` for the corrected pattern: check the definition line before advancing state, then check subsequent lines normally (#797). It also recognizes `read_name() {`, `function read_name() {`, and `function read_name {` as equivalent definition forms, and treats heredoc body lines (from an opening `<<`/`<<-` delimiter to its closing line) as opaque text that never resets scope, even when a literal column-zero `}` appears inside the heredoc body (#812).
- **A hook command must never begin with a PATH-resolved interpreter or bare-word program — Codex runs hooks through a *login* shell, whose PATH omits version-manager tooling.** `codex-rs/hooks/src/engine/command_runner.rs`'s `default_shell_command` executes every hook as `$SHELL -lc "<command>"`. A login shell sources `~/.profile` but **not** `~/.bashrc`, and nvm/fnm/mise/volta all initialize in `~/.bashrc` — so `node`, `python`, `uv`, etc. are simply absent from a hook's PATH on a developer machine where they work fine interactively. The failure is maximally confusing: the hook dies with `hook exited with code 127` before a single line of cenci code runs, so it reads as a cenci bug rather than a PATH one, and it strikes only the events whose command carries the interpreter prefix (flow's `SessionStart`/`PreCompact`/`Stop` died via `node "${PLUGIN_ROOT}/codex/hook-output.mjs"` while the `PreToolUse` guards, which invoke their `.sh` files directly, kept working — making it look like "start/stop hooks are broken"). Write every hook command as a direct `"${PLUGIN_ROOT}/..."`-anchored executable with a `#!/bin/sh` shebang, and keep the hook path's dependencies to what a bare login shell guarantees. Note the asymmetry with `${PLUGIN_ROOT}` itself, which is safe: Codex string-substitutes it into the command *before* the shell ever sees it (`engine/discovery.rs`), and additionally exports it — but only for plugin-bundled hook sources, never config-layer ones (`env: HashMap::new()`). Where a payload genuinely needs a tool (e.g. `jq` for the SessionStart envelope), degrade to a valid empty payload plus a stderr warning and `exit 0` rather than propagating a non-zero exit — an advisory hook must never be why a session fails to start. Enforced by `flow/codex/hooks.test.sh`, which asserts every command in `codex/hooks.json` starts with a quoted `${PLUGIN_ROOT}` path *and* executes each one with `node` masked to exit 127.
- **Unmatched glob patterns are passed literally to tools, not treated as "no matches"** — in Bash's default (non-nullglob) mode, a glob like `.plans/<id>-*.md` that matches no files is passed to grep (or other tools) as a literal filename, causing the tool to attempt to open a file named literally `.plans/<id>-*.md`, which fails with a distinct exit code (grep: `exit 2`, "No such file or directory"). Many checks document their logic as "grep exits 1 → clean pass, anything else → fail closed," expecting `exit 1` to mean "no matches found." However, the unmatched glob produces `exit 2` instead, and if that exit code is mapped to a "fail closed" condition when it actually represents infrastructure error (missing glob matches), the ordinary first-run case silently disables the feature. Use `shopt -s nullglob` before the glob to convert unmatched patterns to an empty string, or wrap glob-based checks with explicit file-existence guards: `[[ -e .plans/<id>-*.md ]] && grep ...`. Always test the tool's exit code behavior with an unmatched glob in the actual environment before documenting or shipping the check (#849).
- **Code you reuse or depend on carries its own preconditions — whether you port it to a new call site or simply build new code atop it in place — and both directions need an explicit audit.** (1) When porting a helper function or code block from one file to another, verify that every precondition the source call site enforces is also enforced at the new call site: preconditions (e.g., "input path must be absolute", "temp file must exist before reading") live at the call site, not inside the helper body, so porting only the algorithm silently breaks termination invariants or security contracts when the new context calls the helper with inputs it doesn't expect. Test the new call site with edge-case inputs that triggered the precondition in the original. Example: a `canonicalize_path` helper was ported between files assuming absolute input (its termination via `${ancestor%/*}` eventually yielding `""` depends on this); the source file had `realpath` absolutization at the call site, but the new script lacked an equivalent step, causing an infinite loop when called on relative paths from `SKILL.md` on first run (#876). (2) When new code creates a dependency on existing surrounding code in place (e.g., extracting a PID from a temp-file-based variable, or depending on a temporary directory root created by a surrounding line), audit that existing code's own safety preconditions. Security-critical rules (e.g., "never use unchecked command substitution for temp directories") that were pre-existing gaps become actively load-bearing when new code depends on them — fix the precondition violation rather than leaving it as latent debt. A focused review of "did I write safe code" can miss surrounding code's failure modes that your new code now depends on; conversely, when you refactor or add dependencies on a surrounding line, verify that the line itself meets its own Critical Rules — new dependence turns old gaps into active risks (#913).
- **In a fail-closed script that blocks operations based on policy violations (e.g., a security guard rejecting unsafe paths), every path that could silently bypass a check must be closed — both in how external commands are checked and in how conditional guards are structured.** (1) The script's safety invariant depends on ALL external-command calls (jq, gh, git, grep) being explicitly checked for failure. A single missing check on one call (e.g., computing a marker-match count) silently falls through to the risky default action, reproducing the exact bug the fail-closed behavior was meant to prevent. Enforce this as a structural rule: either use `set -e` to fail the entire script on any non-zero exit, or grep the entire source file before shipping to verify every external-command call has an explicit `|| return 1` (or similar) check. Inconsistency in an otherwise-disciplined file is the highest-risk case, because the missing check is easy to overlook on review (the pattern works fine everywhere else). Example: in a 700-line fail-closed issue-creation script, two jq calls computing marker-match counts had no exit check while every other jq/gh call in the file did, creating a silent-failure path that could reproduce the duplicate-creation bug the script exists to prevent (#876, CRITICAL finding). This includes `cat` reads of config files/stdin: a bare `RESULT="$(cat "$file")"` silently collapses to empty on failure (unreadable file, stdin error), and downstream jq/JSON processing then treats it as a missing/empty config and may drop all keys on re-write; guard with `if ! RESULT="$(cat "$file")"; then` followed by an error exit, or `RESULT="$(cat "$file")" || return 1` — this matches the security-critical-paths rule in root AGENTS.md. (2) Every conditional guard wrapping a critical invariant check must also have an explicit failure branch — an unguarded `if <condition>; then <check> fi` with no `else` silently disables the check when the condition is false. When a guard's condition can be false (extraction fails, command produces no output, file doesn't match expected shape), the `else` must also fail closed, not silently succeed; this includes guards using output redirection or piped commands, where "success" can mean "ran without error but produced empty output" — a subsequent file-existence or line-count check (`[[ -s file ]]`) only catches the empty case, not the wrong-shape case. Example: a coverage-map sync check that extracts tokens by pattern must fail if (a) the extraction is empty OR (b) the extraction contains wrong-shaped content — both need explicit guards, each with an else-fail-closed path. Recurred twice in #916's Phase 4 implementation of the same fail-closed script, the first instance caught after shipping (by review), the second caught on re-review. Use `if ! <condition>; then fail ...; fi` at the outset to establish the success-case precondition (e.g. "this directory exists, this file contains the right pattern"), then perform the actual check after the guard has established the precondition. (#876, #916) (3) When the fail-closed logic is a parser modelling another interpreter's grammar (e.g. bash's heredoc syntax), test it against that interpreter's real documented behavior, not just the parser's own internal consistency — and when patching one instance of a bug class (e.g. a secret-leak message in one error path), grep the whole file for every other reachable site of the same pattern before calling the fix complete, since a first-pass fix that only clears the initially-flagged instance can recreate the bug via a different path. `bwt_apply_patch_targets`'s heredoc parser passed self-consistent tests while diverging from bash's real `<<-` tab-stripping and exact-line-match terminator semantics (three silent-bypass bugs), and an initial secret-leak fix covering only the exit-8 message site missed an equally-reachable success-path message, both requiring a second review round to catch (#1036).
- **When externally-derived multi-line content (e.g. a commit message read from `git log`, a GitHub comment from an API response, a file path from user input) is used as an argument to a shell command, prefer established safe-channel patterns over direct shell interpolation, and apply them consistently throughout the file.** If the script already uses `--body-file`, `-F`, `--input`, or other file-based content channels for similar external data in one location, reuse that same pattern (or an equivalent safety convention) for all such multi-line content rather than switching to direct `-m "$VAR"` or inline interpolation elsewhere in the file. Direct interpolation of multi-line strings risks command injection and creates an inconsistent security surface that makes review harder and invites future mistakes. Example: a skill using `gh pr comment --body-file` for GitHub-sourced text should similarly use `git commit -F <tmpfile>` for externally-sourced commit messages, not `git commit -m "$externally_sourced_message"`. Pattern consistency within a file serves as a de facto security audit trail: an unusual deviation from the file's established safe-channel pattern becomes visible on review and flags potential injection risks. (#879)
- **When implementing armed-action fixtures (e.g., a signal-trap marker file that triggers on the next invocation), ensure the armed state is cleared immediately after the action fires — do not defer cleanup.** A stale armed marker plus a since-recycled PID (or other recycled resource) can cause the action to trigger on an unrelated target on a future invocation. Pair the armed-trigger check with immediate cleanup on successful firing: e.g., if `[[ -f "$CTL/crash-after-post" ]]` fires a `kill -KILL`, immediately follow with `rm -f "$CTL/crash-after-post" "$CTL/target.pid"` so a later fixture invocation or scenario re-entry cannot re-arm the same marker. (#913)
- **Before executing a destructive operation like `kill -KILL` on a value read from a file or variable, validate the argument is a valid positive integer matching `^[1-9][0-9]*$`, not just non-empty or numeric-looking.** An unchecked `-1`, `0`, or non-numeric value can target a whole process group, broadcast a signal, or cause unexpected behavior — `kill -1 -KILL` is equivalent to `killall -KILL`, which is nearly never intended when targeting a specific recorded PID. Always guard with an explicit regex or arithmetic check before destructive operations on externally-sourced identifiers. (#913)
- **An exit status that is silently dropped or conflated turns a real failure into a passing assertion — two distinct constructs do this, both enforced by `flow/tests/write-verb-residuals-contract.test.sh` (#808).** (1) **In bash assignments concatenating multiple command substitutions, only the LAST substitution's exit status is checked by an `||` guard.** A pattern like `VAR="$(cmd1) $(cmd2)" || fail` silently swallows failures in `cmd1` because bash exits the assignment with `cmd2`'s status only; if `cmd1` fails but `cmd2` succeeds (or is trivial), the `||` guard never fires. This is especially dangerous when the first substitution is a directory-resolution step (e.g., `cd ... && pwd`) and the second is a basename or other quasi-guaranteed-success operation. The fix is to resolve each critical substitution in its own assignment with its own explicit `||` check, then combine already-verified values in a separate unchecked statement: `DIR="$(cd "$(dirname "$path")" && pwd)" || return 1; VAR="${DIR}/$(basename "$path")"` — since `dirname` and `basename` cannot meaningfully fail on valid input, the second assignment is safe without an exit check. (2) **When using `grep -r` (recursive scan) to assert an anti-pattern's absence across a directory tree, unconditionally suppressing stderr with `2>/dev/null` conflates "pattern not found" (exit 1) with "scan error" (exit 2, e.g., permission denied, broken symlink), making it impossible to distinguish a genuinely empty result from a partial scan.** A naive `HITS="$(grep -rlF "pattern" "$dir" 2>/dev/null)"` followed by a `[[ -z "$HITS" ]]` assertion will pass even when part of the tree was never scanned due to I/O errors, violating the test's intent to prove the pattern is absent everywhere. Always capture `grep`'s exit status separately without suppressing stderr, then explicitly check whether the exit code is 1 (success — pattern truly absent) or 2 (failure — scan error, treat as a negative result): `RAW_HITS="$(grep -rlF "pattern" "$dir")"; rc=$?; if [[ $rc -eq 2 ]]; then fail "grep scan error"; fi; HITS="$RAW_HITS"` or use a subshell to separate exit-status capture from piping: `if ! HITS="$(grep -rlF "pattern" "$dir")"; rc=$?; [[ $rc -eq 1 ]]; then fail "grep scan error"; fi`. This ensures the test distinguishes "pattern confirmed absent" from "tree partially unscanned, absence unconfirmed." See that test's lines 289–300 for the corrected pattern.
- **A `#!/bin/sh` script must never assign to a bash-reserved variable name (`BASH_COMMAND`, `BASH_SOURCE`, `BASH_ARGV`, `SECONDS`, `PIPESTATUS`, `RANDOM`, `LINENO`, `FUNCNAME`, …) — `/bin/sh` is bash on macOS, Arch, and Fedora, and bash silently overwrites those names mid-script.** The assignment itself succeeds and every static check passes; bash then resets the variable before each simple command, so a later read returns something else entirely — for `BASH_COMMAND`, the text of the guard's own currently-executing command. This is a fail-**open** failure mode with no diagnostic: both PreToolUse guards (`flow/hooks/scripts/guard-main-worktree.sh`, `flow/hooks/scripts/check-sensitive-files.sh`) stored `tool_input.command` in a variable named `BASH_COMMAND`, so on any bash-`/bin/sh` host their Bash arm inspected the guard's own source text, found no write candidate, and allowed every Bash redirection/`tee` write through with empty stderr and `exit 0` — exactly the bypass class #795/#810 closed for Write/Edit. Reproduce with `/bin/sh -c 'BASH_COMMAND=x; : filler; echo "$BASH_COMMAND"'`. Prefer a name tied to the data (`TOOL_COMMAND`), and avoid the whole `BASH_*` prefix rather than checking a snapshot of today's reserved list — bash keeps adding names to it (`BASH_MONOSECONDS`, `BASH_TRAPSIG`). The CI blind spot that hid this for two releases: `flow-ci.yml` runs on `ubuntu-latest`, where `/bin/sh` is dash and these names are ordinary variables, and both hook suites invoked the hook as `sh <script>` — so CI never executed either hook under bash. Any test suite for a `#!/bin/sh` script must therefore run its full case list under **both** shells; `guard-main-worktree.test.sh` and `check-sensitive-files.test.sh` do this via `HOOK_SHELL` plus a re-exec loop over every locally available shell.
